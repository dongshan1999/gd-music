> 一句话定位：项目不依赖任何测试框架，用 Godot 自带的「场景即测试」模式写测试——每个测试是一个可 headless 运行的 `.tscn` + 脚本，用 `_check()` 收集失败，最终以退出码 `OK/FAILED` 结束，可被命令行或未来的 CI 直接判定。

## 1. 功能概述

- **用户视角**：不面向终端用户，面向开发者。改完代码后运行对应测试场景，看终端里 `push_error` 与最终 `N failures` 输出。
- **实现视角**：
  - 测试脚本全部 `extends Node`（一个例外是 `SceneTree`），在 `_ready()` 里 `call_deferred("_run")` 或直接开跑；
  - 断言靠自建的 `_check(condition, message)` + `_failures` 数组，失败时 `push_error`；
  - 结束时 `get_tree().quit(OK if _failures.is_empty() else FAILED)`（如 `assets/tests/music_app/music_app_download_test.gd:25`），headless 运行时退出码即可判断成败；
  - 测试分三类：**离线结构测试**（不联网、不读写用户资料库）、**联网冒烟**（依赖 Bilibili 网络）、**原生扩展测试**（libmpv / FFmpeg / 封面解析）。

## 2. 功能入口与调用链

### 2.1 运行方式

```bash
# 单个离线测试（headless，推荐）
godot --headless --path . res://assets/tests/music_app/music_app_download_test.tscn

# 需要音频文件的冒烟测试（用环境变量传路径）
SMOKE_AUDIO=/tmp/gdmpv_test_tone.m4a \
  godot --headless --path . res://addons/gdmpv/test/audio_backend_smoke_scene.tscn

# gdmpv 格式矩阵
GDMPV_FORMAT_DIR=/tmp/gdmpv_formats \
  godot --headless --path . res://addons/gdmpv/test/gdmpv_format_matrix_scene.tscn
```

也可以在编辑器里直接打开 `.tscn` 按 F5 运行。`music_app_lyric_parser_test.gd` 是 `extends SceneTree`（`assets/tests/music_app/music_app_lyric_parser_test.gd:1`），没有配套场景，需要用 `--script` 方式或临时挂到场景上运行。

提交前的最小回归集合（三条都离线，逐条 `echo $?` 必须为 0）：

```bash
godot --headless --path . res://assets/tests/music_app/music_app_download_test.tscn
godot --headless --path . res://assets/tests/music_app/music_app_bilibili_test.tscn
godot --headless --path . res://assets/tests/music_app/music_app_ui_test.tscn   # 最慢，起 SubViewport 渲染
```

**沙箱环境提示**：若运行环境无法创建 Godot 的用户数据目录（无写权限的容器/沙箱），headless 可能在启动阶段直接崩在 `signal 11`；把 `HOME` 指到可写目录即可绕过，例如 `HOME=/tmp/godot-home godot --headless --path . <场景>`（推断：由旧环境的运行记录得出，本次未逐台复现）。

### 2.2 单次测试的执行流程

```
运行 .tscn
   └─ 根节点脚本 _ready()
       ├─ （可选）重定向存档路径，隔离用户数据
       ├─ call_deferred("_run")
       └─ _run()
           ├─ 逐个 _test_xxx()
           │    └─ _check(cond, msg) → 失败时 push_error 并记录
           └─ get_tree().quit(OK/FAILED)   ← 退出码即结论
```

## 3. 核心数据结构

## 4. 关键实现

### 4.1 为什么不引第三方测试框架

GUT / GdUnit4 这类框架需要额外插件、额外的场景树约定和编辑器集成，而本项目的测试目标很集中：**验证数据结构与页面生命周期**，不需要 mock 框架、参数化、报告生成。自建 `_check` 大约 5 行代码即可覆盖需求，且：

- headless 可直接跑，无编辑器依赖；
- 退出码语义清晰，接 CI 零适配；
- 测试脚本本身是普通 GDScript，能直接 `preload` 业务脚本，无需任何注册。

代价是没有用例发现、没有报告、没有断言层级——这是有意识的取舍。

### 4.2 数据隔离：测试绝不碰用户资料库

所有涉及存档的测试都会在 `_ready()` 最前面重定向 DX 的存档路径：

```gdscript
# assets/tests/music_app/music_app_download_test.gd:12
DX.save.save_path = OS.get_cache_dir().path_join("gdmusic-download-test/autoload.json")
DX.save.data = DX_SaveData.new()
```

`assets/tests/music_app/music_app_focus_save_test.gd:7`、`assets/tests/music_app/music_app_track_edit_test.gd:24` 用同样的写法（各自独立子目录）。这样做有两个原因：

1. 本地开发时跑测试不会清空真实曲库（历史上有过误删数据的风险）；
2. 测试可重复：每次从空存档开始，结果与上一次运行无关。

下载测试更进一步，只验证「路径规则 + 数据结构」，完全不发网络请求（见 `music_app_download_test.gd` 头部注释），把「下载逻辑」和「网络」解耦。

### 4.3 UI 测试用 SubViewport 模拟多机型

`music_app_ui_test.gd` 不依赖真实窗口，而是创建 `SubViewport` 并切换两种尺寸：

```gdscript
# assets/tests/music_app/music_app_ui_test.gd:28
viewport.size = Vector2i(430, 932)      # 主流手机
# :185
viewport.size = Vector2i(width, 932)    # 窄屏回归（320 等）
```

它遍历 `SceneRegistry.POPUP_SCENES`（`:34`）把每个页面场景都实例化一遍，检查节点存在与布局不溢出，然后触发 `_popup_open` / `close_popup` 验证导航生命周期。这是本仓库最有价值的自动化测试：新增页面若忘记注册或缺少 `%Node`，会直接失败。

这条测试还隐含一条对页面的硬约束：`:37` 只做 `get_scene(id).instantiate()`，**不调用 `setup()`、也不注入控制器**。所以任何弹窗页/页面在 `_ready()` 里都不能假设 controller 已存在，节点必须用 `%NodeName` 取并做空值保护——否则一旦该页面被加进 `POPUP_SCENES`，这条测试就会当场失败（这是它真正拦住的那类回归）。同一测试还用 `page.size.x <= viewport.size.x`（`:77`）做溢出断言，窄屏 320 宽度是硬门槛：长标题要靠 `clip_text` / `text_overrun_behavior` 处理，不能靠撑宽容器。

### 4.4 冒烟测试与环境变量

原生相关能力（libmpv 解码、封面解析）依赖真实媒体文件，仓库只在 `assets/tests/music_app/fixtures/tone.m4a`（约 4.7 KB）放了一个最小样本。测试因此用环境变量传入路径：

- `SMOKE_AUDIO`（`addons/gdmpv/test/audio_backend_smoke_test.gd:5`）：指定待解码音频；
- `GDMPV_FORMAT_DIR`（`addons/gdmpv/test/gdmpv_format_matrix_test.gd:6`）：指定格式矩阵样本目录。

没有环境变量时测试会跳过或退化为结构检查，不会阻塞本地开发。

### 4.5 退出码约定

| 写法 | 语义 |
| --- | --- |
| `quit(OK)` / `quit(0)` | 全部通过 |
| `quit(FAILED)` / `quit(1)` | 有失败用例 |
| `quit()` | 仅用于「提前 return / 环境不满足」的路径（如 `assets/tests/music_app/music_app_focus_save_test.gd:14`） |

注意后两种都会让 `push_error` 在编辑器输出里标红，即使退出码为 0，也应查看输出。

### 4.6 联网冒烟的兜底素材与风控

联网测试最怕「因为搜不到所以整条链路没跑」，`music_app_download_smoke.gd` 对此做了两层设计：

1. **搜索重试**：`search("bilibili", "钢琴", 1)` 最多 3 次，间隔 3 秒（`:52-57`）；有结果时优先挑时长 `< 120` 秒的短视频，下载成本最低。
2. **固定曲目兜底**：搜索仍为空就改用常量拼出的曲目继续验证下载链路——`FALLBACK_BVID = "BV1GJ411x7h7"`、`FALLBACK_CID = 137649199`、`FALLBACK_TITLE = "Never Gonna Give You Up"`、`FALLBACK_ARTIST = "Rick Astley"`、`FALLBACK_DURATION = 213`（`:15-19`），并在输出里打印 `Search skipped (...); falling back to ...`（`:61`）。

兜底存在的原因是**未登录搜索会命中风控**：B 站宁可返回 `code 0` + `v_voucher` 也不报错，插件会判成「Bilibili 触发了风控验证，请稍后重试或切换网络。」（`plugins/builtin/bilibili.gd:508-510`）。兜底让「风控」只降级为「少测了搜索一段」，下载、解码、清理三段照常验证。

测试本身仍然与用户数据隔离：`_ready()` 里把 `DX.save.save_path` 指到 `OS.get_cache_dir()/gdmusic-download-smoke/`（`:33-34`），下载根改到 `temp/music_download_smoke`，结束后删除。

代价是这个兜底把测试和**一个具体视频**绑定了：`BV1GJ411x7h7` 一旦下架、转成会员专享或触发风控，冒烟就会失败，而失败原因看起来像「下载坏了」。排查时先看输出里有没有 `Search skipped`。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 无网络（联网冒烟） | 失败并输出具体请求错误；不应在离线环境作为门禁 |
| 缺 libmpv 动态库 | gdmpv 测试在实例化阶段报错退出，不影响 GDScript 侧测试 |
| 缺音频样本 | 依赖环境变量的测试跳过解码断言 |
| 测试写文件 | 全部落在 `OS.get_cache_dir()/gdmusic-*-test/`，不碰 `user://` 真实存档 |
| 测试超时 | 无超时机制；网络测试挂住需手动 Ctrl+C |
| 页面新增未注册 | UI 测试遍历 `POPUP_SCENES`，新页面若未注册不会被发现（这是覆盖盲区） |
| 搜索被风控（`v_voucher`） | 冒烟降级为固定 `FALLBACK_BVID` 曲目继续跑，输出里打印 `Search skipped`（见 §4.6）；不算测试失败 |
| 页面在 `_ready()` 里假设 controller 已注入 | UI 测试实例化时不调 `setup()`，会直接失败——这正是它想拦住的写法（见 §4.3） |

## 6. 相关测试

本文档描述的即是测试体系本身。自查方式：

1. `godot --headless --path . res://assets/tests/music_app/music_app_download_test.tscn`，观察退出码 `echo $?` 为 0；
2. 在输出中搜 `failures`，确认 `0 failures`；
3. 打开 `music_app_ui_test.tscn` 正常跑完，确认没有 `push_error` 标红。

### 6.1 手动验收矩阵

自动化覆盖不到的部分（真实网络、真实文件、真实平台解码）靠这张表逐条点验，每条对应一个已知会坏的场景：

| # | 场景 | 操作 | 期望 | 相关位置 |
| --- | --- | --- | --- | --- |
| 1 | 单曲下载 | 播放页点下载，观察按钮 | 按钮变百分比并禁用 → 完成后恢复可点；设置 › 音乐下载多一条记录、总占用增加 | `assets/scripts/ui/music_app/views/player/music_app_player_view.gd:297`、`:329` |
| 2 | 离线播放 | 下载完成 → 断网 → 切到别的歌再切回 | 仍能播放（命中本地文件，不请求 `playurl`） | `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:465-477` |
| 3 | 删除下载 | 已下载时再点一次下载按钮 | 提示「已下载，再点一次删除」，确认后文件与记录都消失，再次播放回到在线解析 | `assets/scripts/ui/music_app/views/player/music_app_player_view.gd:297`、`assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:172` |
| 4 | 中断残留 | 下载中途强杀进程 → 重启 → 看目录 | `.part` 被清掉，管理页没有半截记录 | `assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:447-460` |
| 5 | 非音频响应 | 用返回 HTML 的地址构造下载 | 报「下载内容不是有效的音频文件。」，不留文件也不写记录 | `assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:411-421` |
| 6 | 未登录风控 | 未登录搜索同一关键词多次 | 出现「Bilibili 触发了风控验证」提示；登录后重试应成功 | `plugins/builtin/bilibili.gd:508-510` |
| 7 | 移动端解码 | iOS 上「下载 → 播放」 | 能下载、能出现在列表，播放时报缺解码支持 | `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:537-545` |
| 8 | 管理页动作 | 设置 › 音乐下载 → 复制路径 / 打开目录 | 路径进剪贴板 / 系统文件管理器打开下载目录 | `assets/scripts/ui/music_app/controllers/music_app_download_management_controller.gd:39-55` |

第 2 条是最容易「假通过」的一条：只断网切歌不会触发重新解析，必须切到另一首再切回来（或重启 App），才会走 `_resolve_stream_for_track()` 的下载分支。

## 8. 已知限制与后续

- 没有 CI 集成，测试全靠手工触发；
- 无覆盖率统计，插件浏览器/搜索、歌单编辑等交互密集模块缺少单元测试；
- `music_app_ui_test` 只验证「能实例化 + 布局不溢出」，不校验交互结果；
- 联网冒烟测试没有 mock 层，网络波动会导致偶发失败，建议后续为插件 HTTP 层加可注入的传输接口；
- `assets/tests/dx/` 基本为空，DX 框架本身（存档迁移、SAF 路径解析）缺少回归测试。
- **「离线优先不发起请求」没有自动断言**：`music_app_download_test.gd` 是纯数据测试，播放侧的「命中下载记录就不调插件」只能人工验收（§6.1 第 2 条）。要自动断言需要给插件控制器注入可替换的传输层或 spy，当前架构没有这个缝。
- **联网冒烟绑死了一个视频**：`assets/tests/music_app/music_app_download_smoke.gd:15` 的 `FALLBACK_BVID` 一旦下架、转会员或撞风控，冒烟会以「下载失败」的形态报错；且没有 mock 传输层，搜索重试 3 次也救不回来（§4.6）。
- **没有超时与重试框架**：网络类测试挂住只能 Ctrl+C，没有单测级超时；这是自建测试体系换来的简洁性的另一面。
