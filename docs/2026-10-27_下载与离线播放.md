| 项目 | 内容 |

> 一句话定位：把插件曲目「解析直链 → 串行下载成文件 → 登记一条下载索引」，之后播放同一首时优先读本地文件，既不重复请求 playurl，也不依赖 CDN 还在不在。

## 1. 功能概述

- 用户视角：播放页的下载按钮可把当前插件曲目存到本地；下载中按钮显示百分比；已下载再点一次提示「已下载，再点一次删除」；设置页「下载管理」能看到目录、总占用、每首大小与时间，可删除或打开目录。
- 实现视角：下载控制器 `assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd`（505 行，`class_name MusicAppDownloadController`）负责队列、解析、HTTP 下载、落盘、写索引；`controllers/music_app_download_management_controller.gd`（73 行）+ `views/settings/music_app_download_management_view.gd`（108 行）+ `views/settings/music_app_download_row.gd`（67 行）组成管理页；播放侧「离线优先」在 `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:526-538`，通过 `get_download_record()` 与下载控制器解耦。
- 需求边界（R1–R5）：**R1** 播放页能对当前插件曲目发起下载，过程有进度、结束有成功/失败反馈；**R2** 文件落 `user://` 私有目录，重启后仍在，下载记录随存档持久化；**R3** 设置页有「下载管理」入口，能看目录、总占用、逐条列表并删除或打开目录；**R4** 已下载曲目再次播放**不调用**插件 `get_media_source`、不请求 `playurl` 与 CDN，断网可播；**R5** 文档与实现同步（本篇即 R5 的产物）。
- 非目标：不做公开分发/批量爬取；不绕过会员与付费限制；不改插件「只返回带时效直链」的协议；不把文件导出到系统「音乐」目录（iOS/Android 上不可见）。也不做批量下载歌单、断点续传、后台下载服务、限速。

### 2.1 一次下载的完整链路

1. 播放页 `_on_download_pressed()` → `download_track(track)` `assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:123`。
2. 前置校验：曲目为空/无 id → 失败；**已有记录 → 直接返回 `cached: true`**（`:129-131`）；无 `plugin_id` → 失败；同曲目正在下载 → 失败。
3. 入队并 `_set_status(QUEUED)` → `_pump()` `:206`；`_pump()` 串行取队首、`await _do_download(track)` `:221`，完成后递归 `_pump()`。
4. `_do_download()`：`RESOLVING` → `plugin_controller.get_media_source(track)` → 归一化扩展名 → 算目标路径 → 重试循环下载 → magic 校验 → 写 `.part` → `move` 成正式文件 → 建记录 → `set_download_record` + `save(false)` → `DONE`；若正是当前播放曲目，再 `request_audio_sync()`（`:295-296`）让播放器立刻切到本地文件。
5. `download_track()` 用 `while` + 0.1 秒定时器轮询状态，直到 `DONE` / `FAILED` / `CANCELLED` 才返回（`:142-155`）——**它是 await 式接口，UI 调用方拿到的就是最终结果**。

## 3. 核心数据结构

### 3.1 任务状态机 `Status`

| 枚举 | 值 | 含义 | 进入时机 |
| --- | --- | --- | --- |
| `IDLE` | 0 | 从未下载 | `get_status()` 默认值（`:86`） |
| `QUEUED` | 1 | 已入队等待 | `download_track()` `:139` |
| `RESOLVING` | 2 | 正在向插件解析直链 | `_do_download()` `:225` |
| `DOWNLOADING` | 3 | 正在收字节 | `_download_bytes()` `:309` |
| `DONE` | 4 | 已落盘且写索引 | `:293` |
| `FAILED` | 5 | 任一步失败（`last_error` 带原因） | `_fail()` `:485` |
| `CANCELLED` | 6 | 被用户取消 | `_consume_cancel()` `:479` |

`is_downloading()` `:88` 把 `QUEUED` / `RESOLVING` / `DOWNLOADING` 合成「进行中」，UI 只认这一个判断。

### 3.2 控制器字段

| 字段 | 含义 |
| --- | --- |
| `_queue: Array[TrackData]` | 待下载队列 |
| `_status` / `_progress` | `track_id → Status`、`track_id → {received, total}`，只在内存 |
| `_cancelled` | 取消标记（下载中取消要靠它跨 await 传递） |
| `_busy` | 串行闸门 |
| `_active_request` / `_active_track_id` | 当前请求，用于 `cancel_request()` |
| `download_root_relative` | 下载根相对路径，默认 `music_downloads`（测试可改，`:44-45`） |

### 3.3 下载记录 `MusicDownloadRecordData`（持久化）

| 字段 | 含义 |
| --- | --- |
| `track_id` | 与 `TrackData.id` 一致，是去重键 |
| `plugin_id` | 来源插件，用于目录分组与「UP 主/艺人」显示 |
| `media_id` | 插件内媒体 id（优先 `plugin_data.cid`，否则 `id`，`:358-360`） |
| `title` / `artist` | 下载当时的标题与作者（快照；之后曲目改名会由编辑流程同步） |
| `path` | DX 虚拟路径 `app://music_downloads/<plugin>/<hash>.<ext>` |
| `format` | 归一化扩展名 `m4a` / `mp3` / `ogg` / `wav` |
| `bytes` / `duration` | 字节数与时长，供列表展示 |
| `source_url` / `created_at` | 来源页面链接（`build_source_url()` `:190`）、下载完成时间；列表按 `created_at` 倒序（`:97-99`） |

字段校验规则见[存档与数据模型](2026-10-27_存档与数据模型.md) 3.3 节；记录**不写回 `track.file_path`**，原因见 §4.2 与 `assets/scripts/save/music/music_download_record_data.gd:4-10` 的类注释：写回会污染「本地扫描曲目」判定，并在移除本地文件夹时被连带删除。`source_url` 只落存档供追溯，管理页既不展示也不提供复制/打开按钮（不暴露带 `bvid`/`aid` 的外链）。

## 4. 关键实现

### 4.1 为什么串行：`_pump()` 的闸门

文件头注释（`:4-8`）：「串行下载（同一时刻 1 个），其余排队，避免同时占满带宽与插件风控」。实现就是 `_busy` 一个布尔：

```gdscript
func _pump() -> void:
	if _busy or _queue.is_empty():
		return
	_busy = true
	var track: TrackData = _queue.pop_front()
	...  # 空值守卫、_active_request/_active_track_id 清理
	await _do_download(track)
	_busy = false
	_pump()
```

`_pump()` 是**递归续跑**而不是循环，因为 `_do_download()` 里有多个 `await`；用循环会漏掉「await 期间又有新任务入队」。并发上限硬编码为 1，没有可配置项。

### 4.2 设计取舍：独立索引 + 缓存优先

**为什么下载记录不复用 `TrackData.file_path`**——三条候选方案，选 C：

| 方案 | 好处 | 问题 |
| --- | --- | --- |
| A. 写回 `TrackData.file_path` | 播放侧零改动 | `get_local_track_ids()`（`assets/scripts/ui/music_app/controllers/music_app_local_music_controller.gd:27-35`）把「`file_path` 非空」当作本地曲目 → 下载曲目污染本地音乐页，且移除本地文件夹时会被连带删除 |
| B. 给 `TrackData` 加 `download_path` 字段 | 播放解析简单 | 记录跟着曲目走：删曲目就把记录带走、文件成孤儿；设置页无法脱离曲库独立管理 |
| C. **独立下载索引**（`MusicAppStateData.downloads`） | 与曲目生命周期解耦；设置页独立管理；删曲目不删文件 | 多一个数据类 + 一次表查找（`_download_index` 命中为 O(1)） |

选 C 的代价是播放侧要「先查表」，换来一条硬性质：**下载文件的生命周期由设置页控制，而不由曲库控制**。这条取舍写在 `assets/scripts/save/music/music_download_record_data.gd:4-10` 的类注释里，也是「删曲目 ≠ 删文件」（见[存档与数据模型](2026-10-27_存档与数据模型.md)）的设计前提。

**为什么缓存优先、而且必须在插件解析之前查**：`playurl` 返回的 CDN 地址带时效，且每次播放都要为整首重新拉字节，所以「先查本地」不是性能优化而是正确性要求。三条来自插件侧的硬约束决定了实现细节：

| 约束 | 依据 | 对实现的约束 |
| --- | --- | --- |
| 直链带时效、且只有 `get_media_source()` 能拿到 | `plugins/builtin/bilibili.gd:203` 的 `playurl` 参数、`:216-223` 的 `dash.audio` 取址 | **绝不把 URL 写进索引**，每次下载前重新解析；索引里只存文件路径 |
| `headers` 必须原样透传 | 插件 `plugins/builtin/bilibili.gd:237-242` 返回 `user-agent` / `accept` / `accept-encoding` / `referer`（referer 指向稿件页）；下载器 `_build_http_headers()`（`:423-427`）把这份字典原样拼成 `k: v` 行，不自拼 | 少任一头都可能被 CDN 拒（缺 `referer` 会 403，推断）；所以 §4.4 的 403 不重试——4xx 重试也不会好转 |
| cookie 只复用、不写入 | 唯一持久化位置是插件设置里的 `plugin_cookies`（见[插件账号登录](2026-10-27_插件账号登录.md)） | 下载器不存、不改 cookie；登录态只影响解析成功率与可用码率 |

### 4.3 进度上报：0.2 秒轮询

`HTTPRequest` 没有进度信号，只能轮询。`_poll_download_progress()` `:342-352` 起一个与请求并行的协程：每 `PROGRESS_INTERVAL_SECONDS`（0.2s）读 `get_downloaded_bytes()` / `get_body_size()`，写 `_progress` 并发 `download_progress_changed` + `download_state_changed`；循环条件是 `is_instance_valid(request) and not request.is_queued_for_deletion()`，请求被 `queue_free()` 后协程自然结束。播放页 `_refresh_download_button()` `assets/scripts/ui/music_app/views/player/music_app_player_view.gd:332` 用它算百分比，`total <= 0` 时显示 `…`。**为什么 0.2 秒**：每帧刷新会让按钮文本每帧重排，0.2 秒既顺滑又只有 5 次/秒。

### 4.4 失败重试：只重试「可能好转」的错误

`_do_download()` `:249-257` 是最多 `MAX_RETRY_COUNT + 1 = 3` 次尝试的循环，是否重试由 `_download_bytes()` 返回的 `retry` 决定：

| 失败原因 | `retry` | 依据 |
| --- | --- | --- |
| 发起请求失败 / 网络层失败（`RESULT_*` 非 SUCCESS） | ✅ | `:316`、`:331` |
| `HTTP 5xx` | ✅ | `:336` 的 `response_code >= 500` |
| `HTTP 4xx`（403 防盗链/410 过期） | ❌ | 同上，只有 `>= 500` 为真 |
| 响应体为空 | ✅ | `:339` |

三次尝试是背靠背的，**没有退避**。

### 4.5 落盘：先 `.part` 再 rename

```gdscript
var part_path := target_path + PART_SUFFIX
var write_result = DX.files.write_bytes(part_path, body)  # 失败则删 .part 并 _fail
if DX.files.exists(target_path):
	DX.files.delete_file(target_path)
var move_result = DX.files.move(part_path, target_path, true)  # 失败同样删 .part
```

流程（`:268-286`）：建目录 → 写 `.part` → 正式文件存在则先删 → `move` 覆盖。直接写正式路径的话，写一半被杀会留下「看起来下载完了」的坏文件；`.part` 是显式的未完成标记，启动时 `_cleanup_part_files()` `:447-460` 递归清理残留（跳过 `.` 开头项），`_verify_records()` `:435-445` 把「索引在但文件没了」的记录删掉——两者共同保证崩溃后可自愈。写完的字节还要过 `_is_valid_audio()` `:411-421` magic 校验（m4a 看偏移 4 的 `ftyp`、mp3 看 `ID3` 或 `FF E0`、ogg 看 `OggS`，其它格式放行），防止 CDN 在 200 状态下返回 HTML 错误页。

### 4.6 目录与文件名规则

`_build_target_path()` `:372-380`：`<root>/<plugin_id>/<sha256(track.id) 前 16 位>.<ext>`。

| 规则 | 原因 |
| --- | --- |
| 按 `plugin_id` 分目录 | 清理某插件缓存可直接删目录，也便于人工排查 |
| 文件名用 id 的 sha256 前 16 位 | 标题含 `/`、emoji、超长字符，直接用标题会造出非法路径 |
| `plugin_id` 过 `_sanitize_path_segment()` `:429` | 只替换 `\ / : * ? " < > \|`，空格保留（否则无法与插件 id 对账） |
| 扩展名归一化 `_normalize_extension()` `:382` | 插件给 `aac`/`mp4` → 统一存成 `m4a`（同一容器、同一条播放链路）；URL 带 `?` 参数要先剥掉再取后缀（`_extension_from_url()` `:395`） |
| 下载根目录 | `DX.files.app_path("music_downloads")`（`:109`），真实路径由 `DX.files.globalize()` 给出（`:113`），设置页展示的就是它 |

### 4.7 记录去重：按 `track_id` 覆盖

写入侧 `MusicAppStateData.set_download_record()` 先线性找同 id 记录，有则**替换**、无则 `append`；读取侧 `get_download_record()` `:68-80` 命中后还会 `DX.files.is_file()` 验一次，文件不在就当场删记录并保存——**索引永远只代表「文件确实在」**；入队侧开头查记录（`:129`）返回 `cached: true`，重复点下载不会产生第二个文件。归一化还会丢弃 `track_id` 或 `path` 为空的记录、重复 id 保留第一条。

### 4.8 删除：失败要回滚

`remove_download()` `:172-187` 先删记录、再删文件；文件删除失败就把记录塞回去并返回错误（`:181-183` 注释：「避免出现看不见的残留」）。两害相权取「宁可留着记录」——反过来（先删文件后删记录）若写存档失败，用户会看到一条指向空文件的记录。

### 4.9 离线优先：播放侧怎么判定

`assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:526-538`：

```gdscript
func _resolve_stream_for_track(track: TrackData, sync_request_id: int):
	if not track.file_path.is_empty():
		return await _load_local_stream(track.file_path)
	# 已下载的插件曲目优先读本地文件，避免再次请求 playurl 与 CDN。
	var downloads = _get_base_controller().get_download_controller()
	...
	var download_record = downloads.get_download_record(track.id)
	if download_record != null and not download_record.path.is_empty():
		var downloaded_stream = await _load_local_stream(download_record.path)
```

优先级：`track.file_path`（真正的本地曲目）→ **下载记录**（离线优先）→ 插件解析。三处配套：① 播放键 `_get_track_playback_key()` 对已下载曲目返回 `download:<track_id>`，与在线播放的键不同，所以下载完成后即使曲目没变也会重新装载音频流；② 下载文件读失败**不报错**，继续走插件解析（与 `get_download_record()` 的自愈互补）；③ 删除下载后播放页主动 `request_audio_sync()`（`assets/scripts/ui/music_app/views/player/music_app_player_view.gd:315`），立刻切回在线源。

这里只做「挑哪条路径」；本地 m4a 真正怎么解出 PCM（先 `M4ADecoder`、再 FFmpeg、最后原生 loader）见[音频后端与解码](2026-10-27_音频后端与解码.md)，本篇不重复。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 曲目无 `plugin_id` | 下载按钮隐藏（`assets/scripts/ui/music_app/views/player/music_app_player_view.gd:336`），控制器也拒绝 |
| 重复下载 | 返回 `ok: true, cached: true`，复用已有记录；下载中重复点返回「正在下载中。」 |
| 下载内容不是音频（HTML 错误页） | magic 校验失败 →「下载内容不是有效的音频文件。」，不留文件 |
| 响应超过 128MB / 超时 | 分别由 `body_size_limit`（`REMOTE_BODY_SIZE_LIMIT` `:13`）与 60 秒超时（`:12`）失败 |
| 用户取消 | 排队中移出队列并标 `CANCELLED`；下载中 `cancel_request()` + `_cancelled` 标记，`_consume_cancel()` 在下一个检查点短路 |
| 落盘/移动失败 | 删 `.part`，记录不写入，`last_error` 透传 DX 文件层错误 |
| 索引有记录但文件没了 | 读取时自动删记录；启动时 `_verify_records()` 批量清 |
| 删除时文件删不掉 | 记录回滚并返回错误 |
| 下载完成前切到别的歌 | 仍会下完并写记录，只是不触发 `request_audio_sync()` |
| 插件被停用或卸载 | 记录与文件都不受影响（记录只存 `plugin_id` 与路径），管理页照常可见、可删，仍能本地播放；只有「再下载新曲目」需要插件可用 |
| 无持久文件系统的平台（Web） | 没有平台门禁：`user://` 在 Web 上不持久，表现为「索引命中但文件不在」，由 `get_download_record()` 当场删记录（§4.7）自愈，用户看到的是下载丢失 |
| iOS 无 AAC 解码后端 | 能下不能播：文件与记录都保留，播放时 `last_error` 为「当前设备缺少 AAC/M4A 解码支持。桌面版可安装 FFmpeg 后重试。」（`assets/scripts/audio/music_app_m4a_decoder.gd:11`），详见[音频后端与解码](2026-10-27_音频后端与解码.md) |
| 播放链路与下载链路的上限不同 | 播放时远程流是 20 秒 / 64 MiB（`assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:23`、`:563`），下载是 60 秒 / 128 MiB（`assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:12-13`），两者不要混用 |

## 8. 已知限制与后续

- **没有断点续传**：请求不带 `Range`，任何失败都从 0 重新下载；且整个文件先进内存再写盘（`response_body` → `write_bytes`），峰值内存约等于文件大小，128MB 上限就是为这条链路设的。
- **重试无退避**：三次尝试紧邻，抖动网络下可能连续命中同一 CDN 节点；并发上限硬编码为 1，不能并行下多首。
- **不是后台下载**：只挂在 showcase 节点下的 `HTTPRequest`，切后台后能否继续取决于平台对引擎主循环的调度（推断：Android 上会随主循环暂停而停滞）。
- `remove_download()` 不会自动回退「正在播放」的音频流，依赖调用方再发 `request_audio_sync()`；新增删除入口时必须记得补这一步，否则会播到已删除的文件。
- 下载目录没有容量上限/自动清理，`get_total_bytes()` 只用于展示；magic 校验只认 m4a/mp3/ogg 三种头，其它扩展名一律放行。
- **没有容量阈值与 LRU**：设计阶段曾计划「默认 2 GB 上限 + 按最后播放时间淘汰」，但 `MusicDownloadRecordData` 最终只有 11 个字段、**没有 `last_played_at`**，淘汰所需的依据不存在；要做必须先加字段并写迁移。
- **没有统一平台门禁**：设计阶段的 `is_supported()`（按 `OS.get_name()` / `OS.has_feature("web")` 判可用）没有落地，播放页下载按钮在 iOS/Web 上一律显示，只能靠失败提示兜底（见 §5）。
- **索引无法自我重建**：只有单向自愈（有记录、文件不在就删记录）。「有文件、索引缺失」的场景（手改存档、旧版本残留）没有扫描修复入口，用户只能重下；也没有旁挂 `<hash>.json` 元数据文件。
- **`SAVE_VERSION` 升级会连带清空下载记录**：当前 `0.0.2`，`dx/runtime/scripts/managers/save/save_data.gd:9-19` 对版本不匹配的 `music` 段整段丢弃——下载记录随曲库一起没，设计阶段「升版本只作标记」的设想不成立。
- **桌面每次播放下载的 m4a 都要重新转码**：设计阶段的 `_pcm_cache` 二级缓存（`user://music_downloads/_pcm_cache/`）未实现，4 分钟的歌约 1–2 秒转码开销（推断），详见[音频后端与解码](2026-10-27_音频后端与解码.md)。
- **没有自动缓存**：只有手动下载；「播放成功的曲目自动落盘」不在当前实现里。
