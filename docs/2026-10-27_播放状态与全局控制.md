| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-10-27 |
| 对应代码版本 | develop @ 91d939d（工作区 2026-10-27） |
| 功能分类 | 播放内核 / 应用界面 |
| 覆盖范围 | 播放状态控制器（`music_app_audio_controller.gd`）、播放队列控制器（`music_app_playback_controller.gd`）、播放事件、Android 后台媒体控制绑定、音量持久化 |

> 一句话定位：全局只有一份「当前曲目 + 播放队列 + 播放模式 + 已播秒数」的状态，所有页面的播放按钮、进度条、后台通知栏都读写这一份状态，再经一次去抖的 `request_audio_sync()` 落到真正的音频后端。

## 1. 功能概述

- 用户视角：播放/暂停、上一首/下一首、拖动进度条、调音量、切换播放模式（列表循环 / 单曲循环 / 随机），以及在通知栏、锁屏、蓝牙耳机上控制播放。
- 实现视角：
  - `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd`（1431 行，**`class_name MusicAppPlaybackStateController`**）是唯一的状态持有者与「状态 → 后端」的翻译层。
  - `assets/scripts/ui/music_app/controllers/global/music_app_playback_controller.gd`（280 行）负责队列内容、槽位推进与播放模式。
  - 页面（播放页 / 迷你播放器 / 设置页）全部通过 `music_app_controller_base.gd` 的 getter/setter 间接读写，不直接碰播放器节点。
  - 状态本身持久化在曲库存档 `music.playback_state`（见[存档与数据模型](2026-10-27_存档与数据模型.md)）。
- 不在本期范围：均衡器/音效、变速变调、歌词时间轴拖动（歌词有自己的视图逻辑）。

> 命名注意：文件名是 `music_app_audio_controller.gd`，但 `class_name` 是 `MusicAppPlaybackStateController`；仓库中**不存在** `music_app_playback_state_controller.gd`，引用一律走 `MusicAppScriptPaths` 常量。

### 2.1 一句「改状态 → 改声音」的链路

1. 入口只改状态：`set_is_playing()` / `set_elapsed_seconds()`（`:86`、`:83`，最终写进 `get_app_state().playback_state`）。
2. 然后调 `request_audio_sync()` `:306`：`_audio_sync_request_id += 1`，再 `call_deferred("_sync_audio_state_deferred", id)`。
3. `_sync_audio_state()` `:382` 先比对 `sync_request_id != _audio_sync_request_id`，过期请求直接丢弃；再判断「要不要换源 / 要不要 seek / 要不要播」。
4. 需要新音频流时 `_resolve_stream_for_track()` `:465`，把 `AudioStream`（或 libmpv 的 URL）挂到后端并 `play()`，最后发 `PlaybackStartedEvent`、`PlaybackProgressChangedEvent`。

**为什么要请求 ID**：`request_audio_sync()` 在一次用户操作里可能被调用多次（按钮回调、状态 setter、下载完成回调），每次都会 defer；如果不去重，同一帧里会重复解析插件地址、重复 `play()`，表现为「点了下一首又跳回来」或「音量忽大忽小」。ID 比较等价于「只让最后一次 defer 生效」。

### 3.3 播放键：`_get_track_playback_key()`

`:695` 生成的键按优先级是 `file:<路径>` → `download:<记录路径>` → `<track.id>` → `title:<标题>`。**为什么不用 `track.id` 单键**：本地导入的曲目可能没有稳定 id（扫描算出 `local:<sha256>`，但用户可能改路径），而 `file_path` 变了就必须重新加载；反过来插件曲目没有 `file_path`，只能用 id。

## 4. 关键实现

### 4.1 播放/暂停

`toggle_playback()` `:264` 只做三件事：无队列时复位 `is_playing = false`；否则取反；然后 `request_audio_sync()` + `_emit_playback_progress_changed()`。真正的 `play()` / `pause` 在 `_sync_audio_state()` 里：

- 已加载同一首且未在播 → `audio_player.play()` 并从 `elapsed_seconds` 恢复位置（`:421-435`）。
- 正在播但状态是暂停 → `set_paused(true)`，同时把播放器真实位置回写 `elapsed_seconds`（`:409-415`），避免「暂停再播」丢掉这几百毫秒。

### 4.2 曲目切换时的数据解析：插件曲目 vs 本地曲目

`_resolve_stream_for_track()` `:465` 的判定顺序是固定的：

1. `track.file_path` 非空 → 当本地曲目处理：`_load_local_stream()` `:514`。
2. 否则查下载记录（`get_download_controller().get_download_record(track.id)`）→ 有记录就当本地文件读（`:468-477`）。这一步就是「离线优先」。
3. 否则当插件曲目处理：`plugin_controller.get_media_source(track)` 拿 `{url, headers, format}`（`:478-508`），再按格式决定走原生 loader、M4A 解码器还是 FFmpeg 回退。

**关键细节**：第 2 步失败（记录在但文件坏了）不会直接报错，而是继续走到第 3 步联网解析——用户感知是「这次没走本地」，而不是「播放失败」。每一步 await 之后都重新比 `sync_request_id`，避免中途切歌后旧结果覆盖新曲目。

### 4.3 seek 与 750ms 保护窗口

```gdscript
var max_seek_seconds := maxi(0, duration - 1)
var target_seconds := clampi(value, 0, max_seek_seconds)
...
_pending_seek_track_key = desired_track_key
_pending_seek_until_msec = Time.get_ticks_msec() + 750
```

`seek_to_elapsed_seconds()` `:275` 做了两件「防误判」的事：

- **钳到 `duration - 1`**：两个后端都把「seek 到流末尾」当自然结束（`:284-286` 注释），拖到最右端会被当成播完，立刻跳下一首。
- **记 750ms 保护窗**：`VideoStreamPlayer`（FFmpeg 回退）在 seek 后解码器重同步期间会短暂 `finished`，若不拦截就会误切歌。`on_audio_finished()` `:343-348` 命中窗口时只补一次 `request_audio_sync()` 并 return；窗口外的自然结束照常推进。

### 4.4 播放结束回调

`on_audio_finished()` `:333` 被两个播放器节点的 `finished` 信号连到（`assets/scripts/ui/music_app/music_app_showcase.gd:69-74`，用 `bind(audio_player)` 区分来源）。流程：

1. 没有队列 / 不在播 / 信号来自非当前播放器 → 忽略（防止被其他 player 的旧信号打断）。
2. 命中 seek 保护窗 → 只同步，不切歌。
3. 熔断检查 `_is_background_error_streak_exceeded()` `:1162`：8 秒窗口内连续 3 次加载失败就停止自动切歌（`:352-358` 注释说明原因——否则一次坏流会在几十毫秒内把整队列跳完，并在 Android 上反复拉起前台服务导致闪退）。
4. `_emit_playback_finished(track)` → `playback_controller.advance_after_finish()`。

### 4.5 播放模式与队列推进

`advance_after_finish()` `assets/scripts/ui/music_app/controllers/global/music_app_playback_controller.gd:110`：

| 模式 | 结束后的行为 |
| --- | --- |
| `REPEAT_ONE` | 回到同一槽位重播（`play_queue_index(current, true)`） |
| `SHUFFLE` | `_pick_random_queue_index(true)`，保证不会随机到当前这首 |
| 其它（`LOOP_ALL`） | `posmod(index + 1, size)`，到结尾回到开头，不停止 |

「上一首/下一首」的手动切歌走 `step_queue(offset)` `:101` → `_resolve_step_target_index()` `:249`，随机模式下**手动切歌也是随机**——这与多数播放器一致，但要注意它意味着「上一首」在随机模式下不是回退历史。

播放模式只存一个 `int`（0–2），`cycle_playback_mode()` `:42` 用 `posmod(mode + 1, 3)` 循环；按钮文案与图标由 `get_playback_mode_label_key()` `:213` / `get_playback_mode_icon()` `:223` 提供，翻译键是 `music_app.queue.mode.loop_all` / `repeat_one` / `shuffle`。

### 4.6 1 秒 tick 同步

`assets/scripts/ui/music_app/music_app_showcase.gd:64-68` 创建 1.0s 的 `Timer`，`_on_tick()` `:98` 调 `tick_playback_progress()` `:311`：

```gdscript
if not is_playing() or not _player_has_stream(audio_player) or not audio_player.is_playing() or _player_is_paused(audio_player):
	return
```

即：只在「状态说在播 + 后端确实在播 + 没暂停」时才把后端位置回写 `elapsed_seconds`，位置没变就不发事件（`:325-330`）。**为什么用 1 秒而不是 `_process`**：进度条只需要秒级精度，每帧读 `get_playback_position()` 并派发事件会让所有监听者（播放页、迷你播放器、通知栏、歌词）每秒 60 次重排 UI；1 秒 tick 顺带也是后台服务的进度锚点。

### 4.7 音量

`set_playback_volume()` `:1386` → `_apply_playback_volume()` `:1395`：`linear_to_db()` 折算成 dB，**0 视为 -80dB 而不是 `-inf`**（`:1394` 注释），因为部分后端对 `-inf` 会触发断言或直接静音失效。流式后端（libmpv）走 `set_volume_db()`，原生 `AudioStreamPlayer` 走 `volume_db` 属性。持久化在 `user://music_app_settings.cfg` 的 `[playback] volume`（`:1422`），**不进曲库存档**：音量是设备级偏好，多设备同步没有意义，也避免存档版本升级被音量的读写牵连。

### 4.8 后台音频控制绑定：绕过 deferred

`bind_background_audio_controls()` `:107` 把 Android 插件的 `media_control(action: String)` 连到 `_on_background_media_control()` `:116`，支持 `play` / `pause` / `toggle` / `next` / `previous` / `stop` / `seek_to:<毫秒>`。

**这是整份代码里最反直觉的一处**（`:132-136` 注释原文）：该回调是 Java 线程经 `GodotPlugin.emitSignal` **同步**调进来的，而 App 退到后台后 Godot 主循环基本不推进，`request_audio_sync()` 里的 `call_deferred` 可能永远排不上队——表现为「通知栏图标变了，声音没动」。因此这里额外准备了三个**同步直达**的私有方法：

| 方法 | 位置 | 用途 |
| --- | --- | --- |
| `_apply_immediate_transport(playing)` | `:235` | 已加载同一首时直接 `play()` / `set_paused()` |
| `_apply_immediate_seek(seconds)` | `:166` | 直接 `player.seek()`，同样留 1 秒余量 |
| `_apply_immediate_load()` | `:202` | 换曲目时直接 `load_source()`（本地/已下载文件才行；远端直链退回 deferred） |

拖进度条后还要 `_push_background_seek_position()` `:182` 立刻回推位置给 Java 侧，**不能复用** `_dispatch_background_action()` `:1020`：后者的节流 key 是「曲目|艺人|播放态|时长」，位置不在 key 里，同一首内连续拖动会被整段节流掉，Java 侧就会继续用旧基准外推进度。通知栏状态更新本身有 600ms 最小间隔（`BACKGROUND_ACTION_MIN_INTERVAL_MSEC`，`:39`），防止 Android 12+ 上频繁 `startForegroundService` 触发系统限制。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 空队列 | `toggle_playback()` 直接复位 `is_playing`；`tick` 里也再兜一次（`:316-320`） |
| 曲目解析失败 | `_mark_playback_unavailable()` `:970`：`is_playing = false`、`last_error` 有文案、发进度事件让 UI 复位 |
| 插件未安装/未登录 | `get_media_source()` 返回空，`last_error` 透传插件错误文案 |
| 连续加载失败 | 8 秒内 3 次（`:64-65`）→ 停止自动切歌并提示「连续多首音频加载失败，已停止自动切歌。」 |
| 存档里的 `queue_index` 越界 / 曲目被删 | `MusicAppPlaybackStateData.normalize()` 过滤无效 id 并 `clamp`（见[存档与数据模型](2026-10-27_存档与数据模型.md)） |
| 音量文件缺失/损坏 | `_load_playback_settings()` 读失败即保持默认 1.0（全音量） |
| 切歌中途的旧异步结果 | 每个 await 后比对 `_audio_sync_request_id`，过期结果丢弃 |

## 8. 已知限制与后续

- 全局单例式状态：同一时刻只能有一个「当前曲目」，无法多队列并存（例如「稍后播放」列表）。
- `advance_after_finish()` 在 `LOOP_ALL` 模式下到结尾回开头，没有「播完停止」模式；若需要要新增枚举值并同时改 `cycle_playback_mode()` 的 `posmod(…, 3)` 与翻译键。
- 随机模式不做「已播集合」去重，长时间随机可能出现重复（当前只保证不随机到当前这一首）。
- 位置回写精度是 1 秒，进度条拖动后到下一 tick 之间可能有 <1s 的显示回跳。
- 后台同步依赖 libmpv 后端的跨线程锁（`GDMPVPlayer` 内部 mutex）；换成纯 `AudioStreamPlayer` 后端时，后台按钮的即时下发只能保证「状态更新」，声音要等主循环恢复。
