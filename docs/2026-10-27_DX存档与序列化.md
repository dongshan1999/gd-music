# DX 存档与序列化（功能实现文档）

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-10-27 |
| 对应代码版本 | `develop` 分支，工作区 2026-10-27（HEAD `91d939d`） |
| 功能分类 | DX 框架 / 数据存档 |
| 覆盖范围 | `dx/runtime/scripts/managers/save/`、`dx/runtime/scripts/serializer/`、业务侧存档数据脚本 `assets/scripts/save/music/` |

> 一句话定位：DX 只提供一个存档槽 `user://save/data.json`，用「JSON 文本 + 原子替换 + `.bak` 备份 + 超大时分片」把 `DX_SaveData` 这棵对象树持久化；业务数据（歌单、播放进度、插件登录态）挂在 `DX.save.data` 上，改完调用 `DX.save.save()` 落盘。

## 1. 功能概述

- **用户视角**：关闭 App 再打开，歌单、上次播放的曲目与进度、本地音乐目录、插件登录态都还在；进程被杀最多丢最近 60 秒的改动（自动保存间隔）。
- **实现视角**：
  - 读写在 `DX_SaveManager`（`save_manager.gd`），序列化在 `DX_JsonSerializer`（`json_serializer.gd`），业务数据结构在 `DX_SaveData`（`save_data.gd`）→ `MusicAppStateData` / `MusicPluginSettingsData`。
  - 采用「先写临时文件再 rename」的原子写，旧文件先复制为 `.bak`；文件超过 512 KB 时切成多个分片 + 一份 manifest，每片带 `sha256` 校验。
  - 自动保存是"脏标记 + 延迟合并"：`save(false)` 只标脏，主循环在 60 秒后（或每次改动再顺延 3 秒）落盘；退后台/退出时强制立即落盘。
- **不在本期范围**：没有加密、没有压缩、没有二进制格式、没有多存档槽 / 存档截图元数据。

## 3. 核心数据结构

### 3.1 `DX_SaveManager` 常量与字段（`dx/runtime/scripts/managers/save/save_manager.gd:4-18`）

| 成员 | 值 / 类型 | 含义 |
| --- | --- | --- |
| `DEFAULT_SAVE_PATH` | `"user://save/data.json"` | 唯一存档槽 |
| `DEFAULT_SAVE_SPLIT_CHAR_LIMIT` | `512 * 1024` | 超过该字符数改存分片 |
| `SPLIT_SAVE_MARKER` | `"__dx_split_save"` | manifest 标记键，读取时凭它判断是否需要拼片 |
| `SPLIT_SAVE_VERSION` | `1` | 分片格式版本 |
| `SAVE_BACKUP_SUFFIX` / `SAVE_TEMP_SUFFIX` | `".bak"` / `".tmp"` | 备份与临时文件后缀 |
| `AUTO_SAVE_INTERVAL_MSEC` | `60 * 1000` | 首次标脏后的最长等待 |
| `AUTO_SAVE_DELAY_EXTENSION_MSEC` | `3 * 1000` | 每次新改动对落盘时间的顺延量 |
| `save_path` | `String` | 可在运行期改成别的路径（测试用于隔离，见 `assets/tests/music_app/music_app_download_test.gd:12`） |
| `data` | `DX_SaveData` | 业务对象树根 |
| `_is_dirty` / `_next_save_at_msec` | `bool` / `int` | 脏标记与下次落盘时刻 |

### 3.2 存档对象树

| 类 | 路径 | 字段（可持久化） |
| --- | --- | --- |
| `DX_SaveData` | `dx/runtime/scripts/managers/save/save_data.gd:6-7` | `music`（`MusicAppStateData`）、`music_plugins`（`MusicPluginSettingsData`） |
| `MusicAppStateData` | `assets/scripts/save/music/music_app_state_data.gd:15-30` | `version`、`registered_version`、`registered_time`、`tracks`、`playlists`、`playback_state`、`plugin_search_history`、`local_music_folders`、`downloads` |
| `MusicPluginSettingsData` | `assets/scripts/save/music/music_plugin_settings_data.gd:4-7` | `disabled_plugin_ids`、`android_tree_plugins`、`plugin_cookies` |

`MusicAppStateData` 里 4 个运行时索引（`_track_index`、`_track_index_size`、`_download_index`、`_download_index_size`）通过 `_get_save_ignored_fields()`（`assets/scripts/save/music/music_app_state_data.gd:33-39`）排除，注释写明「运行时索引不写入存档，避免存档体积翻倍」。

JSON 顶层因此固定是两段（示意，字段按实际对象树展开）：

```json
{ "music": { "version": "0.0.2", "tracks": [], "playlists": [], "...": "..." },
  "music_plugins": { "disabled_plugin_ids": [], "android_tree_plugins": [], "plugin_cookies": {} } }
```

### 3.3 序列化配置协议（`dx/runtime/scripts/serializer/json_object.gd:4-11`）

每个可序列化对象继承 `DX_JsonObject`，可覆写：

| 返回项 | 作用 |
| --- | --- |
| `{ "属性名": { "ignore": true } }` | 跳过该属性 |
| `{ "属性名": { "json_name": "别名" } }` | 改 JSON 键名 |

默认实现会把 `_get_save_ignored_fields()` 返回的字段名转成 `{"ignore": true}`，所以业务侧只需实现这一个方法。

## 4. 关键实现

### 4.1 原子写入：为什么必须 tmp + bak + rename

```gdscript
# save_manager.gd:200-228（节选）
func _write_json_file_safe(path, payload, pretty := true, backup_existing := true) -> bool:
	var temp_path := _get_temp_path(path)
	... 写 temp ...
	if backup_existing and FileAccess.file_exists(path):
		var current := _try_load_save_payload(path)
		if bool(current.get("ok", false)) and not _copy_file(path, _get_backup_path(path)):
			return false                      # 备份失败则放弃本次写，绝不动旧档
	if FileAccess.file_exists(path):
		DirAccess.remove_absolute(ProjectSettings.globalize_path(path))
	var err := DirAccess.rename_absolute(temp_path, path)
```

三个细节值得注意：

1. **先校验再备份**：只有旧档能被完整解析（`current.ok`）才覆盖 `.bak`，避免把已经损坏的文件"备份"成唯一副本；
2. **rename 而不是覆盖写**：`FileAccess.open(path, WRITE)` 会先把文件截断，写入过程中被杀就得到空文件；rename 在 POSIX 下是原子替换；
3. **写失败保留脏标记**：`_flush_pending_save`（`:340-350`）在 `ok == false` 时把 `_is_dirty` 置回 `true`，下一次 `in_process` 会重试。

### 4.2 分片：绕过单文件过大

当 `json_string.length() > save_split_char_limit`（`:76-77`）时走 `_save_split_json_chunks()`（`:96-142`）：

- 每次保存生成一个 `generation`（`"unix_ticks_usec_randi"`，`:319-320`），分片文件名形如 `data.part.<generation>.000.json`（`:310-317`）；
- 每片写入 `version/generation/index/length/sha256/data` 六个键，长度与哈希同时校验；
- 主文件退化为 manifest：`{"__dx_split_save": true, "part_count": N, "sha256": 整体哈希, "parts": [...]}`；
- 读取时 `_resolve_split_payload()`（`:159-198`）逐片校验 `index`、`length`、`sha256`，再校验拼起来的整体 `sha256`，任一不符即判定失败并回退到 `.bak`；
- 保存成功后 `_cleanup_split_files()`（`:257-275`）删除旧 generation 的分片，但保留 `.bak` manifest 引用到的旧片（`:139-141`），保证回滚仍可读。

设计意图：存档主要是歌单与下载索引，中文标题多、`JSON.stringify` 后长度波动大；单文件过大时一次 `store_string` 阻塞主线程更久，分片把写入切成 512 KB 的块，也降低"写一半崩"的代价。

### 4.3 自动保存的脏标记与延迟合并

```gdscript
# save_manager.gd:332-338
func _mark_dirty() -> void:
	var now_msec := Time.get_ticks_msec()
	if not _is_dirty:
		_is_dirty = true
		_next_save_at_msec = now_msec + AUTO_SAVE_INTERVAL_MSEC
		return
	_next_save_at_msec = maxi(_next_save_at_msec, now_msec) + AUTO_SAVE_DELAY_EXTENSION_MSEC
```

- 第一次改动定下 60 秒后的 deadline；之后每次改动把 deadline 顺延 3 秒，但用 `maxi` 兜住，不会因为持续改动把落盘无限推迟到「永不」以外的更晚（仍以 60 秒为基准滚动）；
- `in_focus(false)` 只对 `OS.has_feature("mobile")` 立即落盘（`:38-43`），注释写明桌面端失焦「只是别的窗口激活了」，此时做整库序列化会卡主线程并饿死按帧喂数据的音频后端——这是本项目 libmpv 播放的踩坑记录。

### 4.4 序列化器：类型驱动的对象树还原

`DX_JsonSerializer.deserialize(data, target)` 不是把 JSON 直接赋给对象，而是**按目标属性的编译期类型**逐项转换：

| 目标类型 | 反序列化行为 | 位置 |
| --- | --- | --- |
| `Vector2/2i/3/3i/4/4i/Rect2/Rect2i/Color` | 从 `{x,y[,z,w]}` / `{pos,size}` / `{r,g,b,a}` 重建 | `dx/runtime/scripts/serializer/json_serializer.gd:517-589` |
| `StringName` / `NodePath` | 字符串转换，非法输入保留原值 | `:325-339` |
| `Array[T]` / `Dictionary[K,V]` | 解析 hint_string 得到元素类型并递归 | `:384-`、`:358-382` |
| `Object` 子类 | 用 hint_string / class_name 反查脚本并 `new()`，再递归填字段 | `:298-323`、`:677-703` |

脚本反查三级回退（`:705-757`）：`type_name 以 .gd 结尾且存在` → `ProjectSettings.get_global_class_list()` 里的 `class_name` → 按类名猜路径递归查找 `res://`。属性类型表按脚本路径缓存，并用「属性名|类型|hint|hint_string|class_name」拼出的签名做失效判断（`:624-663`），支持编辑器里改脚本后热重载。

深度上限 `DEFAULT_MAX_DEPTH = 64`（`:5`），注释直接说明「不支持循环引用，深度护栏防止栈溢出」。任何不支持的类型走 `_report_error()`（`:988`），错误是"记录 + 保留当前值"，不会抛出异常打断整次加载。

### 4.5 版本号与迁移：只有一个「闸门」，没有迁移框架

- 业务存档自带 `SAVE_VERSION = "0.0.2"`（`assets/scripts/save/music/music_app_state_data.gd:6`），写入时由 `normalize()` 强制回填当前版本（`:75-76`）；
- 加载时 `DX_SaveData.sanitize_payload()`（`dx/runtime/scripts/managers/save/save_data.gd:9-19`）检查 `music.version` 是否等于当前 `SAVE_VERSION`，**不等就把整个 `music` 段从 payload 里删掉**，随后 `deserialize` 得到一份全新默认数据，`normalize()` 重建默认歌单/播放状态；
- `MusicAppStateData.compare_versions()`（`assets/scripts/save/music/music_app_state_data.gd:44-61`）提供语义化版本比较，但目前没有调用方做逐版本升级（推断：预留给后续迁移）。

因此当前策略是「版本不符则整体重置业务数据」，`music_plugins`（含插件 cookie）不受影响。这解释了为什么升级后歌单会回到默认——不是加载失败，而是 `sanitize_payload` 主动丢弃。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 存档文件不存在 | 走空 payload → 默认数据 → 立即 `save(true)` 生成初始档（`:62-63`） |
| 主档 JSON 解析失败 / 非对象 | `_try_load_save_payload` 返回 `{ok:false}`，回退 `.bak`，并 `push_warning("Main save is damaged. Loaded backup: ...")`（`:92`） |
| 主档与备份都坏 | payload 为 `null`，`data` 保持 `DX_SaveData.new()` 的默认值，不抛错 |
| 分片缺失 / index 错乱 / 哈希不符 | 逐项校验失败返回 `null`（`:177-197`），等同主档损坏处理 |
| 磁盘写失败 / rename 失败 | `save()` 返回 `false`，脏标记保留，下次自动保存重试 |
| 备份复制失败 | 放弃本次写，旧档保持不变（`:214-217`） |
| 目录不存在 | `_ensure_save_dir()` 递归创建，`ERR_ALREADY_EXISTS` 视为成功（`:66-69`） |
| 进程被强杀 | 最多丢最近一次未落盘的改动（60 秒窗口）；`.tmp` 残留会在下次写前被删除（`:202-203`） |
| 分片清理失败 | 仅 `push_warning`/忽略，不影响存档有效性 |
| 属性类型不可反序列化 | `_report_error` 记录并保留原值，`deserialize` 提前返回（`:27-28`） |

错误码说明：`DX.save.save()` 返回 `bool`（不是错误码枚举）；文件层 API 返回 `{ok, path, error, ...}` 字典，见 [DX文件系统与 SAF](2026-10-27_DX文件系统与SAF.md)。

## 8. 已知限制与后续

- 单存档槽：没有多用户/多档位，`save_path` 只能运行期改，界面层没有暴露；
- 无加密/无压缩：`plugin_cookies`（账号凭据）以明文 JSON 落盘，设备被 root 后可读；中文标题多时 JSON 膨胀明显，分片只解决「单次写入阻塞」，不解决体积；
- 无真正迁移：版本变化即丢弃 `music` 段（见 4.5），用户升级会丢歌单；
- 自动保存靠 `_process` 轮询毫秒时间戳，App 被系统冻结（后台）时不会执行，只能依赖 `in_pause`/`in_quit` 兜底；
- `save()` 是同步阻塞写，主线程直接调用大存档仍会卡帧。
