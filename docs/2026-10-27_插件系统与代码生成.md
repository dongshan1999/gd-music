> 一句话定位：把 MusicFree 生态的 TypeScript 音源批量转成 Godot 能加载的 `.gd` 插件骨架，并在运行时由 `MusicAppPluginController` 从 `user://gdmusic_plugins/` 动态发现、校验、注册、调用——这是「加一个音源不用改 App 主工程、也不用重新发版」的支撑层。

## 1. 功能概述

- **用户视角**：设置 → 插件管理里安装一个 `.gd` 插件（Android 上还可从 SAF 目录导入），搜索页立刻多一个音源；内置 Bilibili 插件开箱可用，手动安装同 id 插件会覆盖内置实现。
- **实现视角**：分成「构建期」和「运行期」两段。
  1. 构建期：`gdmusic_plugin_codegen/scripts/generate_gd_skeletons.js` 读取 22 个 `source_plugins/*/index.ts`，生成 GDScript 骨架 + `manifest.json` + `migration_report.md`，输出到隐藏目录 `.generated/`。
  2. 运行期：`MusicAppPluginController` 把「脚本文件 → `GDScript` → `RefCounted` 实例」动态装载，用鸭子类型（`has_method`）+ 能力声明双重判定，再按需转发搜索 / 播放地址 / 歌词 / 榜单调用。
- **不在本期范围**：生成器不做 TS → GD 的语义翻译（方法体是 TODO stub）；插件没有沙箱与签名校验；不支持从 URL 安装插件（§5 有说明）。

## 4. 关键实现

### 4.1 生成器只做「可接收的骨架」，不做翻译

`gdmusic_plugin_codegen/README.md` 的设计原则第 3、4 条写明「不尝试自动迁移复杂 JS 实现」，只生成元信息、能力声明、依赖标记、方法骨架与 TODO。`buildMethodBlock()`（`generate_gd_skeletons.js:675`）对每个声明过的方法产出形如：

```gdscript
func get_media_source(music_item: Dictionary, quality: String) -> Dictionary:
	## TODO: migrate 酷狗.getMediaSource from MusicFree TypeScript plugin.  ## Source: source_plugins/kugou/index.ts
	push_warning("酷狗.get_media_source() is not implemented.")
	return {}
```

**为什么这么克制**：这 22 个音源大量使用 `axios`、`cheerio`、`crypto-js`（Web 签名）、`webdav` 客户端，语义翻译不可能正确；生成器真正的价值是**把「有哪些方法、什么签名、缺什么依赖」一次性摸清**，让迁移工作量可估算，而不是假装能自动移植。

### 4.2 依赖与难度探测：先给结论再动手

- `DEPENDENCY_RULES`（`generate_gd_skeletons.js:122`）用正则识别 `axios` / `cheerio` / `crypto-js` / `big-integer` / `dayjs` / `form-data` / `he` / `qs` / `webdav`，结果写进骨架的 `JS_DEPENDENCIES`（模板见 `:724`）。
- `CAPABILITY_RULES`（`:134`）识别 `http` / `html_parse` / `crypto` / `webdav_protocol` / `user_variables` / `state_cache` / `pagination`，写进 `MIGRATION_CAPABILITIES`（模板见 `:725`）。
- `estimateMigrationDifficulty()`（`:524`）按能力加权打分（cheerio +3、crypto-js +2、webdav +4、http +1 等），`>=12` 记 `high`、`>=6` 记 `medium`，其余 `low`；`buildMigrationNotes()`（`:564`）把结论拼成中文备注。
- 生成结束写 `manifest.json`（`:966`）与 `migration_report.md`（`:982`），后者是给迁移排期的清单。

### 4.3 输出隔离：为什么是隐藏目录且不写 `class_name`

`buildPluginScript()` 里有一条明确注释：`## class_name intentionally omitted to avoid global script class conflicts in Godot.`（`generate_gd_skeletons.js:713`）。配合默认输出目录 `.generated`（`:6`，README「输出隔离」章节），原因有两条：

1. Godot 会忽略以 `.` 开头的目录，骨架不会被编辑器扫描、不会出现在 `res://` 资源树里；
2. 一旦写 `class_name`，22 个骨架会和运行期真正加载的插件抢同名全局类，编辑器直接加载失败。

因此 `.generated/` 是**人工迁移工作区**，不是运行期依赖。当前工作区里它保留的是 10 个手写迁移实现加 1 个兼容入口（见 §4.4 表格），`manifest.json` 与 `migration_report.md` 属于生成产物，未随仓库提交。

### 4.5 运行时发现与加载

`refresh_plugins()`（`assets/scripts/ui/music_app/controllers/global/music_app_plugin_controller.gd:32`）是整个运行期的收敛点，按固定顺序重建注册表：

1. 遍历 `BUILTIN_PLUGINS`，`save_mode` 标 `builtin`；
2. `_ensure_plugin_root()`（`:385`）确保 `user://gdmusic_plugins` 存在；
3. 扫 `user://gdmusic_plugins/*/plugin.gd`，逐个 `_load_plugin_from_script()`（`:389`）；
4. 扫 `MusicPluginSettingsData.android_tree_plugins` 里登记的 SAF 目录，`_load_android_tree_plugins()`（`:696`）；
5. 同一 `id` 后加载者覆盖先加载者——这就是「手装插件覆盖内置 Bilibili」的实现，也是 `plugins/README.md` 明确记录的行为。

加载器不信任文件内容，先做三道闸门：

```gdscript
# music_app_plugin_controller.gd:679
if source_text.contains('extends "res://plugins/builtin/bilibili.gd"'): return true
if source_text.contains("func get_platform") and source_text.contains("func get_supported_search_types"): return true
if source_text.contains("extends GDMusicPluginBase") or source_text.contains("extends GDMusicPluginMethods"): return true
```

`_validate_plugin_instance()`（`:439`）再要求实例必须实现 `get_platform()` 与 `get_supported_search_types()` 且平台名非空。**为什么要两道**：文本特征过滤掉 `.gd` 里混进来的任意脚本（防误装、防把工具脚本当插件），实例校验则挡住「语法正确但接口不对」的实现——后者只有真正 new 出实例才暴露。

`_load_plugin_from_source()`（`:403`）用 `GDScript.new()` + 源码 + `reload()` 在内存里试装，用于**安装前验证**（`_stage_plugin_script_for_validation()`，`:790`），验证失败不落盘，避免一个坏插件把 `user://` 目录污染成永远加载失败的启动黑洞。

### 4.6 运行时调用与错误隔离

调用全部走同一套模板：取条目 → `has_method` 判定 → `await` → 读插件 `last_error` → 成功才返回。

| 方法 | 位置 | 能力判定 | 失败返回 |
| --- | --- | --- | --- |
| `search()` | `:319` | `has_method("search")` | `{}`，`last_error` 保留原因 |
| `get_media_source()` | `:335` | `has_method("get_media_source")` + 结果 `url` 非空 | `{}`，提示「插件未返回可播放的音频地址」 |
| `get_lyric()` | `:354` | `plugin_data.hasGetLyric` | `{}`，静默 |
| `get_toplists()` | `:371` | `has_method("get_toplists")` | `[]`，静默 |

错误隔离的关键是 `_get_plugin_error()`（`:365`）：它遍历 `get_property_list()` 找名为 `last_error` 的属性。**为什么不用信号或返回值**：插件是第三方手写脚本，宿主无法强制它抛错；「暴露一个叫 `last_error` 的字符串属性」是最低成本的约定——内置插件照做了（`plugins/builtin/bilibili.gd:55` 声明 `var last_error := ""`，在 `:199`、`:226`、`:510` 等处写入具体错误文案），宿主读不到该属性时 `_get_plugin_error()` 返回空串，退化成「静默失败」而非崩溃。注意基类 `gdmusic_plugin_base.gd` **没有**定义 `last_error`，这是纯约定而非契约：`.generated/` 里 10 个手写插件都没有这个属性，所以它们的失败对 UI 完全不可见（§8 记为限制）。同时 `_fail()`（`:848`）统一写宿主的 `last_error`，UI 只读这一个变量。

停用插件在 `_require_plugin_entry()`（`:594`）里就被拦掉，返回「插件已停用，请在设置中启用。」——停用不是卸载，脚本仍在内存里，只是不再被调用。

### 4.7 登录态与 cookie 下发

`MusicPluginSettingsData.plugin_cookies`（`assets/scripts/save/music/music_plugin_settings_data.gd:7`）是唯一持久化位置，桥梁是三个可选方法：

| 宿主方法 | 位置 | 插件侧契约 |
| --- | --- | --- |
| `get_plugin_cookie()` / `set_plugin_cookie()` | `:520`、`:530` | 读存档 / 去掉 `Cookie:` 前缀 → 写存档 → 清 `_applied_cookie` 强制重下发 → `save(false)` |
| `refresh_login_state()` | `:501` | `await plugin.fetch_login_status()`，取 `is_login` / `uname` |
| `_apply_plugin_cookie()` | `:564` | `plugin.set_user_cookie(cookie_header)`，按 cookie 值做幂等 |

`set_plugin_cookie()` 里那句「插件实例可能缓存了旧 cookie，这里强制重新下发」是踩过的坑：插件实例在 `refresh_plugins()` 之间是常驻的，只改存档不会自动生效，必须主动 `erase("_applied_cookie")` 触发一次下发。

### 4.8 热重载

系统没有文件监听，热重载靠「显式刷新 + 延迟刷新」：

- 场景 `_ready()` 结束时 `call_deferred("_auto_refresh_plugins")`（`assets/scripts/ui/music_app/music_app_showcase.gd:78`）保证首帧前完成扫盘而不阻塞 `_ready()`；调试面板 `Refresh Plugins`（`:38`）可随时重建注册表，改完 `plugin.gd` 不用重启 App；
- `refresh_plugins()` 每次都重新 `load()` + `new()`，所以修改会生效，但**播放中的曲目不会被迁移到新实例**，需要重新解析播放地址。

### 4.9 内置 Bilibili：能力面与被下游依赖的部分

`plugins/builtin/bilibili.gd`（823 行）是唯一开箱可用的音源，也是**下载功能唯一的解析来源**。元信息：`VERSION = "0.0.1"`（`:8`）、`SRC_URL`（`:9`）指向 MusicFree 官方 dist 包（`dist/bilibili/index.js`）、每页 `PAGE_SIZE = 50`（`:47`）。

`SUPPORTED_SEARCH_TYPES`（`:11`）只有 `music` / `album` / `artist`，**没有 `sheet`**；`SUPPORTED_METHODS`（`:14-28`）声明 7 个能力（每个都带驼峰别名，如 `get_media_source` / `getMediaSource`），**没有 `get_lyric`**——所以宿主的 `hasGetLyric` 为假，B 站曲目没有歌词（见[歌词解析与显示](2026-10-27_歌词解析与显示.md)）。

| 能力 | 方法 | 界面接入 | 与下载的关系 |
| --- | --- | --- | --- |
| 搜索单曲 / 专辑 / 作者 | `search()` `:96` | 已接；专辑、作者点开由 `open_collection_result()` 转成临时合集（`assets/scripts/ui/music_app/controllers/music_app_plugin_browser_controller.gd:102`、`:116-119`） | 下载入口的来源（见[插件浏览器与搜索](2026-10-27_插件浏览器与搜索.md)） |
| 播放地址 | `get_media_source()` `:191` | 播放与下载共用 | **唯一硬依赖**：下载器只认它返回的 `url` + `headers` |
| 专辑详情 / 作者作品 | `get_album_info()` `:109`、`get_artist_works()` `:132` | 已接（同上临时合集） | 间接：让一批曲目可见可下 |
| 收藏夹导入 | `import_music_sheet()` `:329` | **无 UI 入口** | 批量下载的前提，当前只能单曲下 |
| 排行榜 / 榜单详情 | `get_toplists()` `:245`、`get_toplist_detail()` `:309` | 宿主 `get_toplists()`（`assets/scripts/ui/music_app/controllers/global/music_app_plugin_controller.gd:371`）已暴露，界面未接 | 同上 |

把上表读成一件事：**下载链路对插件的要求只有 `get_media_source()` 返回 `{url, headers}`**，其余能力都只是「怎么找到歌」。这也解释了下载器为什么不认识 B 站 API——它只消费 §3.3 的接口契约，换音源不用改下载器。

两个值得单独记的实现细节：

- **`cid` 兜底**：`playurl` 需要 `cid`，搜索结果不一定带，`_get_cid()`（`:538`）会按 `bvid` / `aid` 再查一次；每首曲目的 `plugin_data.cid` 也正是下载记录 `media_id` 的首选来源。
- **标题序号剥离**：`TITLE_ORDER_PREFIX_PATTERN`（`:13`）配 `_strip_title_order_prefix()`（`:787`），在 `_format_media()`（`:646`）、多 P 专辑分 P 标题（`:125`）、`import_music_sheet()`（`:343`）三处统一剥掉「001.」「01、」，避免序号进曲库与下载记录；下载记录里的标题是下载当时的快照，事后改插件不会回溯改写。

### 4.10 文档与代码不一致处（以代码为准）

以下三处是旧描述与实际实现对不上的地方，本篇按代码写：

| 旧说法 | 出处 | 实际情况（以代码为准） |
| --- | --- | --- |
| 「Android / iOS / Web 当前没有 AAC 解码后端」 | `plugins/README.md:17` | Android **有**：远程 m4a 在 Android 且 FFmpeg 可用时直接走 `_load_remote_ffmpeg_stream()`（`assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:562`），本地 m4a 先试 `M4ADecoder` 再回落 FFmpeg（`:537-547`）。真正没有后端的是 iOS 与 Web：转换器探测对非 `macOS/Windows/Linux` 直接返回空串（`assets/scripts/audio/music_app_m4a_decoder.gd:71-73`），也起不了 FFmpeg 进程 |
| 「下载超时 20 秒、大小上限 64 MiB」 | `plugins/README.md:19` | 那是**播放时**内存拉流的上限（`assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:23`、`:563`）；下载功能另有一套 60 秒 / 128 MiB（`assets/scripts/ui/music_app/controllers/global/music_app_download_controller.gd:12-13`），两者不要混用 |
| 「B 站未按 `quality` 过滤 `dash.audio`」 | 早期分析结论（已无留存出处） | 已实现：`dash.audio` 按 `bandwidth` 升序排序后按 `_quality_to_index(quality)` 取索引（`plugins/builtin/bilibili.gd:216-223`、`:758-766`，`low/standard/high/super` → 0/1/2/3，未知取值回落 1），并与数组长度做 `clampi` |

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 插件目录不存在 | `_ensure_plugin_root()` 递归创建，不报错 |
| 插件语法错误 | `reload()` 失败 → `_fail()` 记 `last_error`，该插件跳过，其余继续 |
| 接口不全（缺 `get_platform`） | `_validate_plugin_instance()` 拒绝并记录目录名 |
| 安装来源不是插件 / 从 URL 安装 | `_looks_like_plugin_source()` 四种特征全不匹配即拒绝；`install_plugin_from_url()`（`:131`）固定返回「Installing GDScript plugins from URL is not supported.」 |
| 批量安装部分失败 | `_summarize_install_failures()`（`:290`）最多展示 3 条失败原因，避免弹窗刷屏 |
| 插件返回非法类型 | 控制器强制回落 `{}` / `[]` / `{"isEnd": true, "data": []}` |
| 停用插件被调用 / 卸载内置插件 | 前者由 `_require_plugin_entry()` 拦截并返回「插件已停用」；后者按 `builtin` 标记拒绝，避免出现「怎么都装不回来」 |

## 8. 已知限制与后续

- 生成器只产出骨架，`TODO` 方法体全为 `push_warning` 空实现；22 个音源里真正可用的只有 Bilibili 与 `.generated/` 中 10 个手写迁移。
- `godot/tests/` 目录在 README 中被引用但工作区不存在，插件基类没有回归测试。
- 没有插件签名/沙箱：装进来的 `plugin.gd` 能读本地文件、发网络请求，安装路径必须由用户显式选择。
- 热重载不迁移播放状态，切歌或多音源同时使用时需重新解析播放地址；后续可给能力标记补 `getAlbumInfo` / `importMusicSheet` 的 UI 入口，并把迁移进度纳入 `migration_report.md` 自动生成。
- **能力有、入口没有**：专辑与作者已接界面，但**收藏夹导入**（`import_music_sheet()`）和**排行榜**（`get_toplists()` / `get_toplist_detail()`）只有宿主方法与插件实现，没有页面入口——「批量下载一个歌单或榜单」在做完这块 UI 之前做不了，下载侧只能单曲下（§4.9 有对照表）。
- **歌词是插件层缺口**：内置 Bilibili 没有 `get_lyric`，下载功能也没有歌词缓存；补齐插件方法后可顺带把歌词存到下载记录旁，但那要先扩展 `MusicDownloadRecordData` 的字段（当前 11 个字段里没有歌词位）。
- **没有「是否可下载」声明**：会员专享/付费内容只能等 `playurl` 返回空地址才知道（`plugins/builtin/bilibili.gd:224-227` 的「可能需要登录或暂不可播放」），UI 无法提前把下载按钮置灰。
- **同一份能力表散在两处**：生成器的 `METHOD_SPECS`（`generate_gd_skeletons.js:49`）与插件内的 `SUPPORTED_METHODS` 是两份手写清单，生成器只读 `source_plugins/`、不与内置插件交叉校验，新增方法要两处同时改。
