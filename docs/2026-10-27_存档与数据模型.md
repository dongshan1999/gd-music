| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-10-27 |
| 对应代码版本 | develop @ 91d939d（工作区 2026-10-27） |
| 功能分类 | 数据存档 |
| 覆盖范围 | `assets/scripts/save/music/` 全部数据类、DX 存档管理器的读写/分片/备份策略、索引重建、版本与损坏容错 |

> 一句话定位：整个 App 只有一份 JSON 存档（`user://save/data.json`），里面同时装着曲库、歌单、播放状态、下载索引和插件凭据；业务代码只操作内存对象，落盘由 `DX_SaveManager` 按「防抖 60 秒 + 退出/切后台立即写」统一处理。

## 1. 功能概述

- 用户视角：加进曲库的歌、建的歌单、喜欢的曲目、上次播到哪、下载了哪些、插件登录态，退出再进都还在；存档坏了也不会直接丢库（还有 `.bak`）。
- 实现视角：三层
  1. 通用存档框架 `dx/runtime/scripts/managers/save/save_manager.gd`（路径、分片、备份、定时）；
  2. 应用存档结构 `dx/runtime/scripts/managers/save/save_data.gd`（把 `music` / `music_plugins` 两个业务段挂到根上）；
  3. 业务数据类 `assets/scripts/save/music/` 下的 `music_app_state_data.gd` 与 5 个条目类，全部继承 `dx/runtime/scripts/serializer/json_object.gd`，靠反射序列化。
- 不在本期范围：云同步、多存档槽、导入/导出 `.json`（代码里没有对应入口）。

## 2. 功能入口与调用链

没有「保存按钮」。所有写路径都是「改内存对象 → 标脏 → 定时/事件驱动落盘」：

1. 页面/控制器拿数据：`MusicAppControllerBase.get_app_state()` `assets/scripts/ui/music_app/controllers/music_app_controller_base.gd:26` 返回 `DX.save.data.music`。
2. 改字段：如 `add_track_controller`、`playlist_controller`、`download_controller` 直接改 `tracks` / `playlists` / `downloads` 数组。
3. `DX.save.save(false)` → `dx/runtime/scripts/managers/save/save_manager.gd:45` `save(force=false)` → `_mark_dirty()` `:332`：首次脏标记把落盘时间定在 +60 秒（`AUTO_SAVE_INTERVAL_MSEC`），之后每次再标脏把时间往后顺延 3 秒（`AUTO_SAVE_DELAY_EXTENSION_MSEC`），相当于「手停 3 秒才写一次」的防抖。
4. `in_process()` `:24` 每帧检查是否到期，到期 `_flush_pending_save()` `:340`。
5. 强制写盘时机：`in_quit()` `:31`、`in_pause(true)` `:34`（切后台立刻写），以及少量关键操作直接 `save(true)`（如插件 cookie 落地、下载完成）。
6. 启动时：`in_ready()` `:20` → `_ensure_save_dir()` + `load()` `:52`；文件不存在会被当成「首次启动」，序列化一次默认结构（`:62-63`）。

### 2.1 桌面失焦为什么不写盘

`in_focus()` `:38-43` 的注释原文：「Desktop focus loss only means another window is active. Serializing the whole library here stalls the main thread and starves frame-fed audio.」——桌面上点一下别的窗口就整库序列化，会卡主线程并把给音频喂帧的时机饿掉（表现为一卡一卡）。所以桌面上失焦**只保留**已排定的自动保存时间，移动端才立即 flush。

## 3. 核心数据结构

### 3.1 存档文件与键名

| 文件 / 键 | 说明 |
| --- | --- |
| `user://save/data.json` | 主存档，`DEFAULT_SAVE_PATH`（`dx/runtime/scripts/managers/save/save_manager.gd:4`） |
| `user://save/data.json.bak` | 上一次成功写入的主存档副本（`SAVE_BACKUP_SUFFIX` `:8`） |
| `user://save/data.json.tmp` | 写入中间文件，成功后 rename 覆盖（`SAVE_TEMP_SUFFIX` `:9`） |
| `user://save/data.part.<generation>.<NNN>.json` | 超过 512KB 时的分片（`DEFAULT_SAVE_SPLIT_CHAR_LIMIT` `:5`，`_get_split_part_path()` `:310`） |
| 根键 `music` | 曲库/歌单/播放状态/下载索引/搜索历史/本地文件夹，对应 `DX_SaveData.music`（`dx/runtime/scripts/managers/save/save_data.gd:6`） |
| 根键 `music_plugins` | 插件禁启用、SAF 目录、cookie，对应 `DX_SaveData.music_plugins`（`:7`）；**菜单里没有开关，只在存档里** |
| `music.version` | `"0.0.2"`，版本门禁键（见 4.5） |
| manifest 键 `__dx_split_save` | 主文件是分片清单而不是数据本身时的标记（`:6`） |

### 3.3 条目类字段

| 类 | 字段（位置） |
| --- | --- |
| `TrackData`（`track_data.gd`） | `id` / `title` / `artist` / `subtitle` / `file_path` / `lyric_path` / `duration`（默认 1，最小 1）/ `preview_start` / `mark` / `source` / `plugin_id` / `plugin_data: Dictionary`，`:4-15` |
| `PlaylistData`（`playlist_data.gd`） | `title` / `count` / `mark` / `tracks: Array[String]` / `deletable`（默认 true），`:4-8` |
| `MusicAppPlaybackStateData` | `selected_track_id` / `selected_playlist_index` / `track_ids` / `queue_index` / `mode`(0–2) / `elapsed_seconds` / `is_playing`，`:13-19` |
| `MusicDownloadRecordData` | `track_id` / `plugin_id` / `media_id` / `title` / `artist` / `path` / `format` / `bytes` / `duration` / `source_url` / `created_at`，`:12-30` |
| `MusicPluginSettingsData` | `disabled_plugin_ids` / `android_tree_plugins`(字典数组) / `plugin_cookies`(字典)，`:4-7` |

曲目 id 的生成规则（`track_data.gd`）：已有 `id` 直接用；否则有 `file_path` 用 `make_local_id(path)` = `"local:" + sha256(路径)`（`:32-36`）；两者都没有时 `make_generated_id()` 拼时间戳+微秒+随机数（`:38-42`）。**为什么本地曲目用路径哈希**：同一文件重复扫描要落在同一条曲目上，否则每次扫描都会多出一份；这也意味着文件移动后会被当成新曲目。

## 4. 关键实现

### 4.1 防丢：写临时文件 → 备份 → rename

`_write_json_file_safe()` `dx/runtime/scripts/managers/save/save_manager.gd:200` 的顺序是：先写 `<path>.tmp` → （如果原文件存在且能解析）复制成 `.bak` → 删原文件 → `rename_absolute()` 把 tmp 换正。任何一步失败都会删掉 tmp 并返回 false，**不会留下半截 JSON**。这是移动端最容易踩的坑：直接 `FileAccess.open(path, WRITE)` 写到一半被系统杀掉，存档就是空的。

### 4.2 大存档分片

曲库到几千首后 JSON 可能超 512KB，而部分平台的单文件写入/读取会明显变慢。`_save_main_json()` `:71-82` 判定长度超限就改走 `_save_split_json_chunks()` `:96`：每片 512KB 字符，片内带 `index` / `length` / `sha256`，主文件退化成 manifest（含总长度与总 sha256）。读取时 `_resolve_split_payload()` `:159` 逐片校验 index、chunk 长度与 sha256，最后再校验拼起来的整体 sha256——**任何一片对不上就整次加载失败**，转而去读 `.bak`，而不是「尽量拼一半」。宁可回退到上一次的完整状态，也不要一个结构正确但内容错位的曲库。

### 4.3 索引失效重建：`get_track_by_id()`

```gdscript
if _track_index_size != tracks.size():
	_rebuild_track_index()
var cached: TrackData = _track_index.get(normalized_id)
if cached != null and is_instance_valid(cached):
	return cached
# 外部直接改写 track.id 会让索引失效，回退重建一次保证结果正确。
_rebuild_track_index()
```

`assets/scripts/save/music/music_app_state_data.gd:95-106` 三级兜底：

1. **数量变化**（增删曲目）→ 重建；
2. **命中且实例有效** → 直接返回（O(1)，播放页每次刷新都要查几十次）；
3. **未命中或实例已释放** → 再重建一次再查。第 3 步是为「有人直接改了 `track.id` 却没走 setter」准备的——索引只在 size 变化时自动重建，改 id 不改 size 会让缓存过期，所以宁可多重建一次。

索引本身不进存档（`:33-39`），否则同一份数据要序列化两遍，体积翻倍。

### 4.4 首次启动默认值

`_init()` `:63-73` 建好默认结构后立刻 `normalize()`。默认值：

| 项 | 默认 |
| --- | --- |
| `tracks` | 空数组（`_build_default_tracks()` `:275`）——不预置示例曲目 |
| `playlists` | 仅一条系统「喜欢」歌单（`_build_default_playlists()` `:278-281`），`title = "__music_app.favorite_playlist__"`、`mark = ""`、`deletable = false` |
| `playback_state` | 全默认（`Mode=0`、`is_playing=false`、`elapsed_seconds=0`） |
| `plugin_search_history` / `local_music_folders` / `downloads` | 空 |
| `registered_version` / `registered_time` | 当前 App 版本 / 当前本地时间 |

「喜欢」歌单用**固定字符串当标题**而不是单独字段，`is_system_favorite_playlist()` `:41` 就靠比较 `title == SYSTEM_FAVORITE_PLAYLIST_ID` 判断；`_ensure_default_favorite_playlist()` `:283` 保证它永远排在第 0 位、不可删、且重复的会被丢掉。**副作用**：用户无法把自建歌单取名成那个字符串（会被当成系统歌单）。

### 4.5 版本迁移与损坏容错

- **版本策略是「不兼容即丢弃」而不是逐版本迁移**：`DX_SaveData.sanitize_payload()` `dx/runtime/scripts/managers/save/save_data.gd:9-19` 在反序列化**之前**检查 `music.version`，只要不是当前 `SAVE_VERSION` 就把整个 `music` 段 `erase` 掉，随后 `normalize()` 重建默认结构。
  - 值：`SAVE_VERSION` 目前是 `"0.0.2"`（`assets/scripts/save/music/music_app_state_data.gd:6`），`assets/tests/music_app/music_app_download_test.gd:109` 断言重载后版本就是这个值。
  - 意图（推断自实现方式）：app 还在快速迭代，写 N 个版本迁移器维护成本远高于「让用户重新扫描本地目录」；插件曲目靠 id 重新解析。代价是**升版本等于清空用户曲库/歌单**，所以改字段时能加字段就别动版本号——`normalize()` 已经能把缺失字段补成默认值。
  - `normalize()` `:75-93` 会无条件把 `version` 写回 `SAVE_VERSION`，所以「读取旧档 → 丢弃 → 新建档 → 立即 save」这一串是原子的（`load()` 之后紧接着就是正常保存流程）。
- **主文件损坏 → 读 `.bak`**：`_load_main_payload()` `:84-94` 先试主文件（解析失败/不是 JSON 对象/分片校验失败都算失败），失败再试 `.bak`，成功时 `push_warning("Main save is damaged. Loaded backup: %s")`。两份都坏则从默认值开始，**不会抛异常**。
- **加载后必归一化**：`load()` `:55-60` → 反序列化 → `_normalize_object()` `:328` 递归调 `normalize()`。所有数据类的 `normalize()` 都必须是幂等、且能接受任意脏数据（字段缺失、类型错、id 重复、索引越界）。

### 4.6 归一化清单（`normalize()` 到底修了什么）

| 数据 | 修复内容 | 位置 |
| --- | --- | --- |
| 曲目 | 字段 strip、id 为空则按路径/生成补齐、`duration` 至少 1、`preview_start` 钳进 `[0, duration]`、**按 id 去重**（保留第一条） | `assets/scripts/save/music/track_data.gd:17-30`、`assets/scripts/save/music/music_app_state_data.gd:119-133` |
| 歌单 | 丢弃 `mark == "__plugin_collection__"` 的临时视图歌单（插件专辑页），清理不存在的 track id、`count` 重算、系统「喜欢」去重+固定标题+不可删+置顶 | `assets/scripts/save/music/music_app_state_data.gd:135-170` |
| 播放状态 | `track_ids` 过滤无效 id、`queue_index` 钳位、`selected_track_id` 强制等于 `track_ids[queue_index]`、空队列整体复位 | `assets/scripts/save/music/music_app_playback_state_data.gd:21-38` |
| 搜索历史 | 去空、去重、截断到 10 条 | `assets/scripts/save/music/music_app_state_data.gd:91`、`:172` |
| 本地文件夹 | 反斜杠转 `/`、去尾斜杠（但保留 `C:/` 这种根）、去重 | `:183-192` |
| 下载记录 | `normalize()` 后丢弃 `track_id` 或 `path` 为空的、按 track_id 去重（**重复时保留第一条**） | `:247-261` |
| 插件设置 | 禁启用 id 去空去重；`android_tree_plugins` 三项（plugin_id/tree_uri/relative_path）必须齐全且 plugin_id 唯一；cookie 去 `Cookie:` 前缀、空值丢弃 | `assets/scripts/save/music/music_plugin_settings_data.gd:9-52` |

`playback_state.normalize()` 里 `selected_track_id = track_ids[queue_index]`（`:36`）这条容易误解：它意味着**存档里的 `selected_track_id` 是派生字段**，手改它会被下一次加载覆盖；真正决定「播哪首」的是 `queue_index` 在队列中的位置。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 首次启动无存档 | `load()` 发现文件不存在 → 用默认结构 `save(true)` 建一份（`:52-63`） |
| `music.version` 不匹配 | 整段 `music` 被丢弃并重建默认（清了曲库/歌单/播放状态），只 `music_plugins` 保留 |
| 主存档 JSON 语法损坏 | 回落到 `.bak` 并 warn；再失败则默认结构 |
| 分片缺失/被改 | 校验失败 → 视为主档损坏 → `.bak` |
| 存档目录不可写 | `_ensure_save_dir()` `:66` 失败 → `_save_main_json()` 返回 false，**内存数据仍在**，下次保存重试 |
| 写盘过程中崩溃 | 只有 `.tmp` 可能残缺，主档与 `.bak` 不受影响 |
| 关闭游戏瞬间有未落盘改动 | `in_quit()` `:31` 强制 flush |
| Android 切后台 | `in_pause(true)` `:34` 立即 flush（系统可能随时杀进程） |
| 曲目被删但下载还在 | 下载记录与 `tracks` **解耦**（`assets/scripts/save/music/music_app_state_data.gd:23-24` 注释）：曲目移除后文件仍保留 |
| 运行时索引与数组不同步 | `get_track_by_id()` / `get_download_record()` 按 size 变化自动重建 |

## 8. 已知限制与后续

- 版本不兼容即丢弃：升 `SAVE_VERSION` 会清空用户曲库/歌单（插件 cookie 不受影响），没有迁移器也没有「备份旧档」提示。
- 没有导出/导入入口，用户无法自行备份曲库。
- `.bak` 只保留一代；连续两次坏写会把可用副本覆盖掉。
- 分片阈值是「字符数」而不是字节数，含中文的存档实际字节数会更大；512KB 字符约等于 1–1.5MB 文件。
- `local_music_folders` 只是路径字符串，SAF 授权失效后不会自动剔除（要靠扫描时逐个报错）。
- `plugin_cookies` 是明文存在 JSON 里（`assets/scripts/save/music/music_plugin_settings_data.gd:6` 注释只承诺「只落本地存档，不打日志」），存档文件本身没有加密——多账号/共享设备场景需要额外考虑。
