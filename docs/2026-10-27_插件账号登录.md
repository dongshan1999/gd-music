> 一句话定位：插件账号登录目前只有 B 站一条链路 —— 扫码拿 `SESSDATA` 等 cookie，白名单清洗后写进存档，再分发到插件实例的 `set_user_cookie()`，插件每次请求自行把它拼进 `Cookie` 头。

## 1. 功能概述

- 用户视角：插件管理页里 bilibili 行出现「登录账号」→ 弹窗自动申请二维码 → 手机 B 站 App 扫码确认 → 提示文案依次变成「已扫码，请在手机上确认登录」「登录成功，正在保存凭据…」→ 成功后 toast 并自动关闭弹窗；弹窗里还有「刷新二维码」和折叠的「手动粘贴 Cookie」入口。
- 实现视角分四层，职责很干净：

| 层 | 文件 | 职责 |
| --- | --- | --- |
| UI / 轮询 | `music_app_bilibili_login_popup.gd`（209 行） | 弹窗状态、二维码贴图、2 秒轮询 Timer、手动粘贴 |
| 登录协议 | `music_app_plugin_login_controller.gd`（282 行） | 申请二维码、轮询状态、解析 cookie、校验 cookie |
| 凭据存储 | `controllers/global/music_app_plugin_controller.gd` | `plugin_cookies` 读写、登录态缓存、分发到插件 |
| 插件侧 | `plugins/builtin/bilibili.gd` | `set_user_cookie()` / `fetch_login_status()` / 请求时带 cookie |

- **与任务描述的偏差（以真实代码为准）**：**没有账号密码登录**。协议实现只有二维码（`generate_qrcode()` / `poll_qrcode()`，`assets/scripts/ui/music_app/controllers/music_app_plugin_login_controller.gd:41` `:56`）加手动粘贴 cookie 两个入口，没有任何 `passport-login` 账号密码接口调用。

## 2. 功能入口与调用链

| 入口 | 触发位置 | 处理函数 |
| --- | --- | --- |
| 管理页行内「登录账号」 | `assets/scripts/ui/music_app/views/settings/music_app_plugin_management_view.gd:243` | `show_popup(PopupId.MUSIC_APP_BILIBILI_LOGIN)` + `popup.setup(...)` |
| 弹窗初始化 | `assets/scripts/popup/music_app_bilibili_login_popup.gd:36` | `setup()` → 建登录控制器 → `_sync_login_state()` |
| 弹窗每次显示 | `:63` | `on_popup_shown()`：还没有二维码就申请，未登录则重新同步登录态 |
| 二维码轮询 | `:144` | `_on_poll_timeout()` |
| 刷新二维码 | `:197` | `_on_refresh_pressed()` |
| 手动粘贴提交 | `:174` | `_on_apply_pressed()` → `_apply_cookie()` |
| 关闭弹窗 | `:71` | `close_popup()` 先 `_stop_polling()` |

扫码登录的完整链路：

1. `setup()` 先 `await _sync_login_state()`：已登录就直接显示账号名、隐藏二维码，不再申请新的（`:36-45`）；未登录才 `await _request_qrcode()`。
2. `_request_qrcode()`（`:96`）→ `login_controller.generate_qrcode()` → `_request(GENERATE_URL, {"source": LOGIN_SOURCE})`，返回 `data.url`（二维码内容）与 `data.qrcode_key`（轮询用的 key）。
3. `QrCodeScript.encode_image(url, QR_PIXELS_PER_MODULE, QR_QUIET_ZONE)` 本地渲染成 `ImageTexture` 贴到 `LoginQrTexture`（`:115-130`），不依赖第三方二维码图床。
4. `_start_polling()`（`:133`）启动 2 秒 Timer，每次超时调 `login_controller.poll_qrcode(_qrcode_key)`。
5. 返回码 0 时 `_apply_cookie(cookie_header)`（`:181`）：写 cookie 成功则 toast「登录成功（uname）」并 `close_popup()`；写失败则把消息写进提示标签，允许继续扫码。
6. 写 cookie 的落点：`MusicAppPluginController.set_plugin_cookie()`（`assets/scripts/ui/music_app/controllers/global/music_app_plugin_controller.gd:530`）→ `_apply_plugin_cookie()`（`:564`）调插件 `set_user_cookie()` + `save_manager.save(false)` 立即落盘。

## 3. 核心数据结构

Cookie 白名单（`assets/scripts/ui/music_app/controllers/music_app_plugin_login_controller.gd:21-30`），只保留这些字段：

| 字段 | 作用 |
| --- | --- |
| `SESSDATA` | 登录会话凭据，B 站接口鉴权的核心字段 |
| `bili_jct` | CSRF token，写操作需要 |
| `DedeUserID` / `DedeUserID__ckMd5` | 用户 id 与其校验值 |
| `sid` | 会话辅助标识 |
| `buvid3` / `buvid4` / `b_nut` | 设备指纹，用于风控与 WBI 签名参数 |

注释说明了白名单的意图：`# 只保留这些字段，避免把网关塞过来的杂项 cookie 一起存下来`（`:20`）。

登录状态码（`:19` 附近与 `:56-84` 的分支）：

| code | 含义 | 弹窗表现 |
| --- | --- | --- |
| `0` | 登录成功 | 写入 cookie，toast 后关闭 |
| `86101` | 未扫码 | 「等待扫码」 |
| `86090` | 已扫码待确认 | 「已扫码，请在手机上确认登录」 |
| `86038` | 二维码失效 | 停 Timer、隐藏二维码，提示「二维码已失效。」，按钮改为「刷新二维码」 |
| 其它 | 失败 / 网络异常 | `last_error` 透传 |

| 数据 | 位置 | 说明 |
| --- | --- | --- |

| 登录态缓存 | `MusicAppPluginController._login_states[plugin_id]`（`assets/scripts/ui/music_app/controllers/global/music_app_plugin_controller.gd:12`） | `{logged_in, uname}`，只读缓存，进程内 |

## 4. 关键实现

### 4.1 无 cookie 时根本不发请求

`bilibili.gd` 的 `fetch_login_status()`（`:568`）第一条分支就是短路：

```gdscript
# 没有用户 cookie 时不发网络请求：匿名 nav 必然返回未登录，等它只会拖慢界面
```

这个设计把「列表页刷新登录态」的成本从「每个插件一次 nav 请求」降到零 —— 没登录就是没登录，不需要问服务端。只有存在 cookie 时才 `_ensure_cookie()` 后请求 `https://api.bilibili.com/x/web-interface/nav`。

### 4.2 超时兜底：HTTPRequest 的 timeout 靠不住

`_request()`（`assets/scripts/ui/music_app/controllers/music_app_plugin_login_controller.gd:128`）是整条链路的稳定性核心，它做了三件反直觉的事：

1. **桌面优先 curl**：`_request_via_curl()`（`:209`）在 macOS/Linux/Windows 上用系统 `curl.exe` / `/usr/bin/curl`，`-s -i --max-time 8`。注释给出的理由：这类请求量极小，curl 比 HTTPRequest 稳得多。
2. **自计时兜底**：即使走 HTTPRequest，也自己按 `max_frames = int((REQUEST_TIMEOUT_SECONDS + 5.0) * 60.0)` 数帧（`:177-193`），超时 `cancel_request()` 并再试一次 curl。注释：`HTTPRequest 的 timeout 只管建连，卡住时必须靠这里兜底`。
3. **用 `process_frame` 而不是 `SceneTreeTimer` 做计时**：前者每帧必发，即使主线程被其它 await 卡住也能推进，最不容易漏掉超时。

都不成功时 `last_error` 统一写成「连接 B 站超时，请检查网络后重试。」，弹窗侧直接展示，不抛异常。

### 4.3 cookie 提取：Set-Cookie 可能被合并进一行

`_extract_cookie_header()`（`:254`）遍历响应头，只收 `set-cookie:` 开头的行，并且**按逗号再切一次**（上游可能把多条 `Set-Cookie` 合并进一行），最后按 `COOKIE_WHITELIST` 的顺序拼成 `k=v; k=v`。按白名单顺序拼而不是按响应顺序，是为了让同一账号两次登录产出的 cookie 字符串稳定可比，存档 diff 不会因为顺序抖动。

### 4.4 写 cookie 前先验活，失败回滚

`apply_cookie()`（`:86-105`）的顺序是「先备份 → 写入 → 用新 cookie 问一次 nav → 失败回滚」：

```gdscript
# 校验失败的 cookie 会回滚，避免把无效凭据写进存档
```

具体做法：读 `previous_cookie` → `set_plugin_cookie()` → `await fetch_plugin_login_status()` 看 `logged_in` → 仍然失败就把 `previous_cookie` 写回去并返回「Cookie 无效或已过期，请重新获取。」。空字符串入参不是「校验空 cookie」，而是「退出登录」语义（`:93-96`）。

### 4.5 注入链路：写存档 + 立刻下发到插件实例

`set_plugin_cookie()`（`assets/scripts/ui/music_app/controllers/global/music_app_plugin_controller.gd:530-554`）做了四步：去 `Cookie:` 前缀 → 空则 `erase` 否则写值 → `normalize()` → **强制重新下发**：

```gdscript
entry.erase("_applied_cookie")
_apply_plugin_cookie(entry)
```

`_apply_plugin_cookie()` 调插件的 `set_user_cookie()`，而 `plugins/builtin/bilibili.gd:551` 的 `set_user_cookie()` 除了解析 cookie，还会清空 `_cookie` / `_wbi_img` / `_wbi_sub` / `_wbi_sync_date`，明确注释：`设备指纹缓存可能属于上一个身份，清掉让下次重新获取`。这一步很关键 —— 换账号后如果 WBI 缓存不重置，签名会带着旧身份的设备参数，接口会返回异常。

插件侧 `_build_cookie_header()`（`plugins/builtin/bilibili.gd:621`）才是最终拼头的地方：用户 cookie 优先，缺 `buvid3/buvid4` 时用 `_ensure_cookie()` 拿到的匿名值补齐。

### 4.6 退出登录

`logout()`（`assets/scripts/ui/music_app/controllers/music_app_plugin_login_controller.gd:122-125`）就是 `set_plugin_cookie(PLUGIN_ID, "")`。没有服务端注销调用 —— B 站退出依赖前端丢弃 `SESSDATA`，清掉本地存档即等于退出；同时 `_login_states` 会在下次 `fetch_login_status()` 时因为无 cookie 直接返回未登录（见 4.1）。

### 4.7 弹窗打开即同步状态、忙锁防重入

`_sync_login_state()`（`:75`）根据当前登录态切换两套文案：已登录显示「已登录：<uname>」+ 隐藏二维码 + 提示「当前账号已登录，搜索会带上登录凭据。」+ 按钮文案「重新扫码登录」；未登录显示「未登录（匿名访问，可能被风控拦截）」。`_request_qrcode()` 用 `_is_busy` 做防重入（`:97-99`），并且 `_on_refresh_pressed()`（`:197-201`）里有一句很实在的兜底：

```gdscript
# 上一次申请可能卡死在网络 await 上（协程不会恢复），这里强制解锁后重来
if _is_busy:
    _is_busy = false
```

因为申请二维码是 `await` 的，网络卡死时协程不会恢复、`_is_busy` 会永久为 true，用户只能靠这里的强制解锁恢复。

### 4.8 登录态对下游功能的影响

登录不是独立功能，它的价值全部体现在**搜索与解析的成功率**上。按链路拆开看：

| 环节 | 登录后的变化 | 依据 |
| --- | --- | --- |
| 搜索 | 匿名走 spi 设备指纹，命中风控时 B 站仍返回 `code 0`，但 `data` 里只有 `v_voucher` 没有结果，插件判成「Bilibili 触发了风控验证，请稍后重试或切换网络。」 | `plugins/builtin/bilibili.gd:508-510` |
| 解析（`playurl`） | cookie 影响能否拿到 `dash.audio` 与可用的最高码率（会员档位由 cookie 决定）；拿不到就报「该视频没有可用的音频流，可能需要登录或暂不可播放。」 | `plugins/builtin/bilibili.gd:224-227` |
| 下载 | 下载器**不接触 cookie**：请求头完全来自插件返回的 `headers`（含 `referer`），cookie 由插件在 `_build_cookie_header()`（`:621`）里自己拼进 API 请求 | `plugins/builtin/bilibili.gd:237-242` |
| 已下载文件 | 与登录态无关：命中下载记录就走本地文件，不再解析（见[下载与离线播放](2026-10-27_下载与离线播放.md)）；退出登录、换账号都不影响已下载曲目播放 | `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:465-477` |

三条由此推出的结论：

1. **下载记录里没有凭据**：`MusicDownloadRecordData` 的 11 个字段不含 cookie/token，重装或换账号后下载记录依然有效——这是刻意设计，避免把凭据复制到第二份存档里。
2. **登录失效不会立刻暴露**：插件只在解析/搜索时才真正使用 cookie，界面上的「已登录」来自 `_login_states` 这次进程内的缓存（§3 字段表）；cookie 在服务端失效后，用户先看到的是「解析失败」而不是「登录失效」，需要手动重新扫码或刷新登录态。
3. **风控与登录是两个失败源**：风控表现为「搜不到结果」且错误文案明确提到风控，登录不足表现为「没有可用的音频流」，两种提示不要合并——合并后无法判断该去重新登录还是等一会儿再试。

## 5. 边界与失败处理

| 情形 | 行为 |
| --- | --- |
| 无 cookie | `fetch_login_status()` 直接返回 `is_login=false`，不发请求（`plugins/builtin/bilibili.gd:568-578`） |
| 二维码申请失败 | `last_error` 设为「二维码申请失败，请稍后重试。」，弹窗展示错误（`login_controller:41-54`） |
| 二维码过期 | 轮询返回 `86038`：停 Timer、隐藏二维码、提示「二维码已失效。」（`popup:154-159`） |
| 登录成功但响应没带凭据 | `_extract_cookie_header()` 为空 → `last_error`「登录成功但未拿到登录凭据，请重试。」 |
| cookie 无效 | `apply_cookie()` 回滚旧值并提示「Cookie 无效或已过期，请重新获取。」 |
| 网络超时 | curl → HTTPRequest 自计时 → 再 curl，全失败给统一超时文案 |
| 关闭弹窗 | `close_popup()` 先停 Timer 再 `super`，避免关掉后仍在轮询（`:71-73`） |
| 手动粘贴空串 | 弹窗层先拦截并提示「请先粘贴 cookie。」（`popup:174-179`）；若直接调控制器，空串等于「退出登录」（`login_controller:93-96`） |

## 8. 已知限制与后续

- 登录类型写死：`PLUGIN_ID := "bilibili"`（`assets/scripts/ui/music_app/controllers/music_app_plugin_login_controller.gd:7`），只有 B 站；其它支持 `fetch_login_status` 的插件暂时没有登录 UI。要泛化需要把二维码协议抽成插件方法（如 `generate_login_qrcode` / `poll_login_qrcode`）。
- 只有扫码与手动粘贴，没有账号密码登录；依赖手机端 App。
- cookie 明文存放于 `user://save/data.json`，没有加密也没有过期时间戳；唯一的质量保证是写入前验活 + 失败回滚。
- 轮询固定 2 秒且没有本地倒计时，二维码失效完全依赖服务端返回 `86038`。
- 退出登录不调服务端接口，只清本地；如果 B 站侧会话仍有效，重新粘贴同一份 cookie 仍能登录。
- `_is_busy` 的强制解锁是 workaround：更干净的做法是给申请二维码加显式超时后置位，而不是靠用户点「刷新」来恢复。
