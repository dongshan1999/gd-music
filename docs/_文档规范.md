# gd-music 功能实现文档规范

本目录（`docs/`）按「一个功能 = 一份文档」组织。本文规定所有功能实现文档的统一命名、结构与写作要求，新增文档必须遵循。

## 1. 命名规则

```
YYYY-MM-DD_功能名.md
```

- **时间**：文档生成日期，格式 `YYYY-MM-DD`，本次统一为 `2026-10-27`。
- **功能名**：使用简体中文，能直接对应一个用户可见功能或一个明确的实现域，例如 `播放器页`、`下载与离线播放`、`DX文件系统与SAF`。
- 同一功能若后续大改，新建一份新日期文档并在旧文档顶部标注「已被 `<新文件名>` 取代」，不要直接覆盖历史记录。
- 不使用空格、斜杠、冒号；需要分词时用中文直接连写或下划线。

## 2. 文档结构模板

每份文档按下列 8 节组织，节标题编号固定，便于横向对照：

```markdown
# 功能名（功能实现文档）

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-10-27 |
| 对应代码版本 | develop @ 91d939d（工作区 2026-10-27） |
| 功能分类 | 应用界面 / 播放内核 / 音源插件 / 数据存档 / DX 框架 / 工程化 |
| 覆盖范围 | 本功能实际涉及的脚本、场景、原生模块 |

> 一句话定位：用一两句话说明这个功能对用户意味着什么、在代码里由谁负责。

## 1. 功能概述
- 用户视角：能做什么、在哪些界面出现。
- 实现视角：由哪些类/场景承担，采用什么模式（MVC 控制器、弹窗页面、管理器等）。
- 不在本期范围的能力（如果有），明确写出，避免读者误解。

## 2. 功能入口与调用链
- 入口清单：按钮/手势/系统事件 → 入口脚本函数。
- 用编号步骤或 mermaid 流程图描述「界面 → controller → 全局控制器 → 底层/存储」的完整链路。
- 关键节点标注 `文件路径:行号`。

## 3. 核心数据结构
- 涉及的类、字段、枚举、信号、存档键。
- 表格形式：字段/成员 | 类型 | 含义 | 持久化位置。
- 若数据来自插件返回或网络 JSON，给出实际字段样例。

## 4. 关键实现
按子功能拆小节（4.1、4.2 …），每节讲清：
- 怎么做（算法、时序、状态机、节流/重试策略）；
- 为什么这么做（设计意图、踩过的坑、平台差异）；
- 关键代码位置 `文件路径:行号`，必要时贴 3–10 行核心片段。

## 5. 边界与失败处理
- 空数据/空队列/无权限/网络失败/文件缺失/平台不支持时的行为。
- 并发、节流、去重、超时、内存上限等约束。
- 失败后是否会污染存档，如何恢复。

## 6. 相关测试
- 列出覆盖该功能的测试脚本与场景路径，说明每条测试验证什么。
- 没有自动化测试时写「无自动化测试」，并给出可手工复现的验证步骤。

## 7. 相关文件清单
| 路径 | 作用 |
| --- | --- |
| `assets/scripts/...` | …… |

## 8. 已知限制与后续
- 明确的 TODO、平台限制、未来扩展点。没有则写「暂无」。
```

**节标题的允许替换**（仅限下列情形，其余一律按模板原名）：
- 清单类文档（如《音源插件清单》）：§2 可写成「音源清单总表」，把入口/调用链并入 §4。
- 多管理器/组件总览（如《DX通用管理器与UI组件》）：§3 可写成「管理器与组件清单」。
- §6 可在原名后加限定语（如「相关测试与业务接线」「相关测试与业务用法」）。

## 3. 写作要求

1. **必须基于真实代码**：写作前逐个打开相关文件确认；引用路径、类名、函数名、常量值必须与代码一致，禁止臆造。
2. **行号必须核对**：写 `file:line` 前用 `grep -n` 或读文件确认；代码若有变动，以当前工作区为准。
3. **路径相对项目根**：统一写成 `assets/scripts/...`、`dx/runtime/...`，不要写本机绝对路径（如 `/Users/mac/...`）。
4. **中文为主，标识符不翻译**：类名、函数名、配置键、枚举值保持原文。
5. **讲清「为什么」**：代码注释里已有的设计意图（例如为什么不用 AudioStreamPlayer、为什么要串行下载）必须保留进文档，这是文档的核心价值。
6. **篇幅**：每篇不少于 80 行、建议 120–260 行；宁精不滥，不写空话套话，不复制整段源码。
7. **不改代码**：文档任务只允许在 `docs/` 下新增或修改 Markdown，不得改动任何 `.gd` / `.tscn` / 配置。
8. **链接**：文档内部引用其它文档时使用相对链接 `[播放器页](2026-10-27_播放器页.md)`。
9. **事实核验标注**：无法从代码确认的推断，用「（推断）」标注；不要用模糊表述冒充事实。

## 5. 归档、合并与删除规则

docs/ 只保留「当前仍然有效」的文档，历史材料不在这里堆叠。

1. **一律按功能归档，不按时间堆文件**：一份功能一份 `YYYY-MM-DD_功能名.md`；日期只是生成批次，不代表新旧。
2. **旧文档的处理顺序**：
   - 先 diff：逐章判定「已被新文档覆盖 / 仍有效且独有 / 已过时」；
   - 独有且有效的内容**并入**对应功能文档的原小节（长进 §1–§8 里，禁止另起「附录：来自旧方案」整块，否则等于制造新的重复）；
   - 只丢过程性内容：排期、进度打勾、变更记录、待确认问题、已完成的实施步骤叙述；
   - 合并完成后**删除旧文件**，并清掉所有指向它的链接 / 「见 xx 手册」字样（改成本文自引用）。
3. **删除前必须确认可恢复**：旧文档至少进过 git（已提交或已 `git add`），删除后可 `git log -- <path>` 找回；纯本地未入库的文档不删。
4. **不允许两份文档讲同一件事**：发现同一功能被拆成多篇且内容重叠时，合并成一篇；确属不同层（如业务页 vs 框架能力）则各自只讲本层，另一层只留一句指路。
5. **旧日期文件名不再保留**：本目录只允许存在 `YYYY-MM-DD_<功能名>.md`、`README.md`、`_文档规范.md` 三类文件；历史版本靠 git 历史，不靠在目录里并存多份。
