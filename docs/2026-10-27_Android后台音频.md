> 一句话定位：Godot 只管解码出声，Android 前台服务负责「不被杀 + 通知栏/锁屏可控 + 媒体键可响应」；两者通过一个 `media_control(String)` 信号和一组 Java 方法双向通信。

## 1. 功能概述

- **用户视角**：退出 App 或锁屏后音乐继续播；通知栏、锁屏、耳机线控能播/暂停/上下首；拖动通知栏进度条能跳转；通知卡片显示标题、歌手、封面。
- **实现视角**：Godot Android 插件 `GDMusicBackgroundAudioPlugin`（`JavaSingleton`，导出为 GDScript 单例 `GDMusicBackgroundAudio`）+ `GDMusicBackgroundService`（`Service`，持 `MediaSession`、`Notification`、`WakeLock`、音频焦点）；GDScript 侧全部逻辑收敛在 `MusicAppAudioController` 的后台媒体控制分支。
- **不在本期范围**：不做系统级「正在播放」库索引、不做音频可视化、不做 Android Auto；不接管通知栏的自定义布局（统一用 `Notification.MediaStyle`）。

## 4. 关键实现

### 4.1 为什么用「前台服务 + 系统解码器仍在 Godot」

`android/plugins/GDMusicBackgroundAudio/GDMusicBackgroundService.java:25` 的类注释一句话点明：`Owns Android's background playback lifetime while Godot remains the decoder.`。App 切后台后 Godot 主循环会停滞，但音频线程/驱动仍在跑；系统只要还有前台服务，就不会把进程当缓存回收。因此服务**不碰解码**，只负责生命周期、通知、媒体会话、唤醒锁与音频焦点——避免「同一首歌两个解码器」。

### 4.2 通知栏按钮为什么要用 `getForegroundService`

这是本模块最大的坑，`createAction()`（`:416`–`:434`）里留了长注释：

```java
// ⚠ 必须用 getForegroundService：应用退到后台后，系统禁止后台进程
// 通过 startService 拉起新组件；getService 构造的 PendingIntent 会被静默丢弃，
// 表现为「点了暂停/下一首，通知栏图标变了但没有声音」。
pendingIntent = PendingIntent.getForegroundService(this, action.hashCode(), actionIntent, flags);
```

同时 `PendingIntent` 在 Android 12+ 必须带 `FLAG_IMMUTABLE`（`:419`），`action.hashCode()` 当 requestCode 保证不同按钮不互相覆盖。

这个坑的隐蔽性值得单独记一笔：`PendingIntent.getService()` 最终调的是 `Context.startService()`，而 Android 8 起后台进程就不允许 `startService` 拉起新组件（12 起更严），**系统对 `PendingIntent` 内部的失败不报错、不重试、不打日志**——logcat 里连 `onStartCommand` 都不会出现，只能看到「通知栏图标变了、声音没动」。所以这不是「偶发」而是「必然静默失败」，换 `getForegroundService()` 后一次修复。

### 4.3 Android 12+ 的 `startForegroundService` 时序

`_dispatch_background_action()`（`assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:1081`）的注释记录了线上现象：`startForegroundService` 发出后服务若没在时限内 `startForeground`，再来一次 `startForegroundService` 会让系统把 `ServiceRecord` 判死并抛 `RemoteServiceException(ForegroundServiceDidNotStartInTime)`。旧实现里 `start()`、`updatePlayback()`、`set_is_playing()` 各自都会唤起服务，一次点击触发三四次，必崩。

现行做法（`:1081` 起）：

- **所有常规状态推送统一收敛到 `updatePlayback()`**，只有会话初始化才走 `start()`；
- 用 `key = "title|artist|playing|duration"` 做 600ms 节流（`BACKGROUND_ACTION_MIN_INTERVAL_MSEC`，`:44`）；
- `stop` 也走节流：服务还没 `startForeground` 就被 stop，logcat 会出现 `Bringing down service while still waiting for start foreground`；
- `startForeground` 在 `onStartCommand` 里**先发通知再改 MediaSession**（`:174`–`:182`），保证期限约束优先满足。

### 4.4 进度外推与「拖动却不生效」

服务端不轮询 Godot，而是自己外推：`pushPlaybackState()`（`:474`）用 `positionBase + elapsed` 算当前位置，`speed` 在 1.0 / 0.0 间切；播放中 `scheduleProgressTicker()`（`:499`）每秒重推一次（`:79`–`:92` 的 `progressTicker` 用 `postDelayed` 自调度），避免系统按速度外推漂移——`:470`–`:473` 的注释就是为小米 HyperOS 的媒体卡片/灵动岛进度条写的：只下发一次，几秒后进度就不动了。

坑在 GDScript 侧：`_push_background_seek_position()`（`:243`）注释说明，`seek_to:` 之后**不能**复用常规推送——常规推送的节流键不含位置，拖动中的位置会被节流丢掉，而服务会继续从旧基准外推，表现为「松手又跳回去」。所以 seek 分支直接调 `plugin.updatePlayback(...)` 并同步对齐 `_background_action_key` / `_background_action_at_msec`（`:258`–`:259`）。

要让系统（尤其锁屏与通知栏那两个进度条）真的允许拖动，三件事缺一不可，任何一条不满足都表现为「进度条能拖但松手弹回」或「根本拖不动」：

| 必要条件 | 代码落点 | 不满足时的现象 |
| --- | --- | --- |
| `actions` 必须含 `ACTION_SEEK_TO` | `:445`、`:483`，两个构建点都要加 | 系统认为「此会话不支持 seek」，手指一碰就回弹 |
| 位置不能是 `PLAYBACK_POSITION_UNKNOWN`，且要持续刷新 | `PLAYBACK_STATE_REFRESH_MS = 1000L`（`:62`）+ `scheduleProgressTicker()`（`:499`） | 进度条停在原地或显示 `--:--` |
| 按「基准位置 + 基准时刻」外推，`updateTime` 用 `SystemClock.elapsedRealtime()` | `positionBaseMillis` / `positionBaseElapsedRealtime`（`:76`、`:77`）、`:460`–`:461` | 用 `System.currentTimeMillis()` 作 `updateTime` 会让系统外推出错，位置乱跳 |

前两条对应「小米 HyperOS 对漂移特别敏感」那类问题时容易被误判成「系统不支持」，实际是 actions 或刷新缺失。

真机实测（Redmi 23113RKC6C / HyperOS 3，build 82 日志）：`dumpsys media_session` 里 `actions=823`（= PLAY|PAUSE|PLAY_PAUSE|SKIP_TO_NEXT|SKIP_TO_PREVIOUS|SEEK_TO|STOP 的位或），位置随时间推进 `8000 → 17000 → 33000` 毫秒，锁屏拖动后 `onSeekTo 246906` → 回读 `position=248000`，链路闭合。

App 内的播放页拖动是另一层，走的是「拖动中只预览、松手才 seek」的拆分（`_preview_progress_drag()` / `_seek_player_from_global_x()` + 350ms settle 窗口），见 [libmpv原生扩展](2026-10-27_libmpv原生扩展.md) §4.3；两处不是一回事：**App 内是 GDScript 直连播放器，后台是 Java MediaSession → 信号 → GDScript**，各有各的去重。

### 4.5 后台线程回调不能靠 `call_deferred`

`_on_background_media_control()`（`:121`）里那条 ⚠ 注释是核心设计约束：

> 这个回调是 Java 线程经由 `GodotPlugin.emitSignal` 同步调进来的，而 App 退到后台后 Godot 主循环基本不再推进，`request_audio_sync()` 里的 `call_deferred` 可能永远排不上队 —— 表现为「点了暂停/播放，通知栏图标变了但声音不动」。

因此后台媒体动作一律走三个 `_apply_immediate_*` 快路径：`_apply_immediate_seek`（`:227`）、`_apply_immediate_load`（`:263`）、`_apply_immediate_transport`（`:296`），直接对 `GDMPVPlayer` 下发同步命令（其内部有 mutex，允许跨线程调用，见 [libmpv原生扩展](2026-10-27_libmpv原生扩展.md) §4.2）。

`seek` 还有一处防「误判播完」：目标秒数被夹到 `duration - 1`（`:227` 起），否则精确 seek 到末尾会触发 `END_FILE`，歌单直接跳下一首。

### 4.6 音频焦点与唤醒锁

- 焦点：`initializeAudioFocus()`（`:215`）注册监听；`AUDIOFOCUS_LOSS` / `LOSS_TRANSIENT` 时 `paused = true` 并回传 `MEDIA_PAUSE`（`:220`–`:221`），`AUDIOFOCUS_GAIN` 且原本未暂停则重新申请（`:228`）。Android 8+ 用 `AudioFocusRequest`（`:239`），低版本回退 `requestAudioFocus(listener, STREAM_MUSIC, GAIN)`（`:313`–`:316`）。
- 唤醒锁：`PARTIAL_WAKE_LOCK` + 非引用计数（`:211`），只在实际播放时 `acquire()`，暂停/停止/`onDestroy` 都 `release()`（`:189` 的 `onDestroy` 顺序是 `removeCallbacks` → 释放焦点 → 释放锁 → 释放 MediaSession）。

### 4.7 通知与封面

- `buildNotification()`（`:344`）：`Notification.MediaStyle` + `setShowActionsInCompactView(0, 1, 2)`（`:397`），三个动作固定为上一首/播放暂停/下一首；`smallIcon` 用系统 `android.R.drawable.ic_media_play`（第三方插件不能带自定义 drawable 资源，直接用 App 资源会编译不过）；播放中 `ongoing=true`，`CATEGORY_TRANSPORT`、`VISIBILITY_PUBLIC`、Android 12+ `FOREGROUND_SERVICE_IMMEDIATE`。
- 通道：`createNotificationChannel()`（`:517`）用 `IMPORTANCE_DEFAULT`；`CHANNEL_ID` 带 `_v2` 后缀是因为通道重要性创建后不可提升，老用户已建的 LOW 通道收不到可见通知，只能换 id。
- 封面：`updateArtwork(base64)` → `decodeArtwork()` 解出 `Bitmap`，失败返回 `null`（不抛异常，保证「没封面也能出通知」）。GDScript 侧 `_push_notification_artwork()`（`:1308`）按「曲目 id + 图源」去重，空图源会显式发空串清掉上一首的图；`await` 解析完会**再次校验**当前曲目仍是同一首，避免慢网络下把旧封面贴到新歌上。
- `updateNotification()`（`:506`）捕获 `SecurityException`：Android 13 用户撤销通知权限后 `notify()` 会抛，不捕获会连带把服务搞挂。

### 4.8 构建：源码与清单都在插件目录，产物在 Gradle 工程

`aar-build/plugin/build.gradle` 的关键设计是**不把源码和清单放进 Gradle 工程**，两者都在构建前从插件目录同步过去：

```gradle
// 插件源码保持在 ../ 下，构建前复制到 build 目录，避免把 AAR 输出目录当成源码目录。
def generatedPluginSources = layout.buildDirectory.dir('generated-plugin-src')
// 清单同理：插件根目录的 AndroidManifest.xml 是唯一事实源，
// 构建时复制一份并去掉 package 属性（AGP 8 改用 namespace，保留它会直接报错）。
def generatedPluginManifest = layout.buildDirectory.dir('generated-plugin-manifest')

android {
    sourceSets {
        main {
            java.srcDirs = [generatedPluginSources.get().asFile]
            manifest.srcFile generatedPluginManifest.get().asFile.toPath()
                    .resolve('AndroidManifest.xml').toFile()
        }
    }
}

tasks.register('syncPluginManifest') {
    def source = file('../../AndroidManifest.xml')
    inputs.file(source)
    outputs.dir(generatedPluginManifest)
    doLast {
        def outDir = generatedPluginManifest.get().asFile
        outDir.mkdirs()
        def text = source.getText('UTF-8').replaceAll(/\s+package="[^"]*"/, '')
        new File(outDir, 'AndroidManifest.xml').setText(text, 'UTF-8')
    }
}

tasks.named('preBuild') { dependsOn 'syncPluginSources', 'syncPluginManifest' }
```

**清单要单独同步、还得去掉 `package` 属性，是踩过坑才补的**：`android { namespace }` 只负责给清单写包名，不提供 `<service>`。早先的构建脚本只同步 Java 源码，AGP 便生成了一个**没有任何声明的空清单**（201 字节，仅 `package` 与 `uses-sdk`），而失败信号极其隐蔽：

1. Gradle 构建成功，`classes.jar` 里类齐全，`aapt2 dump` 看 APK 也不报错；
2. 但 AAR 合并进 APK 的清单里既没有 `<service>`，也没有 `org.godotengine.plugin.v1.GDMusicBackgroundAudio` 的 `meta-data`，于是插件注册表不初始化、`startForegroundService()` 没有目标服务 —— 表现成**「通知栏媒体控制和灵动岛整体消失，但播放、后台不断音、封面全部正常」**（类还在 dex 里，所以不崩溃、不报错）。

对照证据：上一版可用 AAR（提交 `0cfed38`，11,318 字节）内清单 910 字节，含 4 条权限、`<service foregroundServiceType="mediaPlayback">` 与插件 `meta-data`；修复后 958 字节，内容与之一致。

构建与替换：

```bash
cd android/plugins/GDMusicBackgroundAudio/aar-build
JAVA_HOME=<JDK 17> ./gradlew :plugin:assembleRelease        # 产物：plugin/build/outputs/aar/plugin-release.aar
cp plugin/build/outputs/aar/plugin-release.aar \
   ../GDMusicBackgroundAudio.aar                             # 约 14 KB（14,397 字节）
```

AGP 8.6.1 要 JDK 17（本机 `.tools/jdk-17.0.20.1+1`）；沙箱里跑 Gradle 必须能写 `~/.gradle`，否则 wrapper 直接 `Operation not permitted`。`compileOnly` 依赖指向 `android/build/libs/debug/godot-lib.template_debug.aar`（Godot 导出 Android 时生成），`minSdk 24` / `compileSdk 36` / Java 17。产物靠 `.gdap` 的 `binary` 字段被 Godot 打包。

### 4.9 为什么不用 PiP 小窗，也不用伪造焦点心跳

要理解这个模块为什么长成这样，得先看它替代了什么。Android 上引擎失焦会**主动停音频**：引擎在 `main_loop_focusout()` 里派发 `NOTIFICATION_APPLICATION_FOCUS_OUT` 之后调用音频驱动的 `set_pause(true)`（引擎源码 `platform/android/os_android.cpp`，不在本仓库），唯一例外是 PiP 小窗模式。所以在 mpv 之前，「退到后台继续播」只能靠两种绕法：

| 绕法 | 做法 | 为什么被弃用 |
| --- | --- | --- |
| 伪造焦点心跳 | 收到焦点丢失后每 2 秒补发一次伪造的「获得焦点」事件，把引擎状态掰回去 | 依赖引擎内部事件时序，通知栏下拉、分屏、系统弹窗任一变化就失效；伪造事件还会污染其他监听焦点状态的模块 |
| PiP 小窗 | 让 App 进画中画，使 `is_in_pip_mode()` 为真，引擎便不暂停 | 只能解 Android，iOS 无对应机制；纯音频进 PiP 需要用户额外授权，且必须一直盯着小窗 |

现在的分层是：mpv 后端不走 `AudioServer`，引擎暂停的是自己的音频驱动，对 mpv 无效；UI 侧则用 `PROCESS_MODE_ALWAYS`（`assets/scripts/ui/music_app/music_app_showcase.gd:51-52`，注释写明「Keep the audio pipeline processing while Android pauses the UI Activity」）让播放器节点在 Activity 暂停时继续被 `_process` 推进。于是「后台不断音」不再需要任何伪造或小窗技巧，只剩「别被系统杀」这一件纯 Android 的事——由前台服务负责。

### 4.10 后台自动切歌：靠前台服务的秒级 tick 驱动

用户动作（切歌、暂停、拖进度）都有 Java 侧 `media_control` 同步回调这条门铃（§4.5），而「mpv 自然播完」没有：它走 `MPV_EVENT_END_FILE` → `GDMPVPlayer::_dispatch_finished()`（`addons/gdmpv/src/gdmpv_player.cpp:215-217`）里的 `call_deferred("emit_signal", "finished")`。后台主循环不推进，这条延迟调用就永远排不上队，于是出现「前台播完正常切歌、锁屏/后台播完原地停住」的差异。

修法是复用既有通道，让 Java 每秒「敲门」：

- `progressTicker.run()`（`android/plugins/GDMusicBackgroundAudio/GDMusicBackgroundService.java:79-88`）每秒先 `GDMusicBackgroundAudioPlugin.dispatchMediaControl("tick")`，再推通知状态；
- `_on_background_media_control()` 新增 `"tick"` 分支 → `_poll_background_playback_end()`：同步查播放器状态，判定「已经播完」就自己走一遍 `on_audio_finished(null)`，再补一次 `_apply_immediate_load()` —— 后台没有主循环，`advance_after_finish()` 里排队的那次加载同样不会执行。

「播完了」的判定（`_player_reached_end()`）刻意和 `_sync_streaming_playback()` 的后台分支用同一套依据，因为 mpv 在这个状态下的特征很明确：

| 状态 | `is_playing()` | `is_paused()` | 位置 |
| --- | --- | --- | --- |
| 自然播完（EOF） | false | false | 停在结尾（≈ duration） |
| 用户暂停 | false | true | 停在暂停点 |
| 主动 `stop()` | false | false | 被复位成 0 |
| 播放出错 | false | false | 停在出错点，但 `last_error` 非空 |

所以判定条件是「不 playing 且不 paused 且 `last_error` 为空」，位置只作兜底：位置 > 1 秒时要求「duration 未知或位置 ≥ duration − 2 秒」；位置已被归零时改看控制器记录的进度（`get_elapsed_seconds() > 3` 才算播完）。这条兜底是给「EOF 之后把位置复位成 0」的后端留的——曾经因为死守「位置 > 1 秒」，真机上播完被一直判定成没播完。

两处去重，避免同一次播完被处理两遍：

- `AUTO_FINISH_DEDUPE_MSEC = 1500` 时间窗 —— tick 与姗姗来迟的 `finished` 落在同一秒内时只处理一次；
- `_on_backend_finished()` 的陈旧信号守卫 —— 若当前播放器**正在播放**（说明 tick 已经切到下一首），这条 `finished` 就是上一首遗留的，直接丢弃。

真机诊断：tick 走到判定失败时会打印 `[MusicAppAudio] tick 未判定播完 pos=… dur=… paused=… err=…`，判定通过则打印 `[MusicAppAudio] tick 巡检：队列 18 → 19，下发=true，playing=true`。这两行是「后台播完不切歌」这类问题唯一可靠的现场证据，别删。

边界：Godot 原生后端（`AudioStreamPlayer`）播完会把位置归零且拿不到 duration，`_player_reached_end()` 只能靠 `get_elapsed_seconds()` 兜底；它本来也不承担后台播放（后台只走 libmpv 后端）。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 非 Android 平台 | `_get_background_audio_plugin()`（`:1057`）直接返回 `null`，`bind_background_audio_controls()` 什么也不做 |
| AAR 未打进 APK | `Engine.get_singleton()` 返回 `null`，只 `push_warning`，播放本身不受影响 |
| Java 方法探测 | `_plugin_has_java_method()`（`:1067`）必须用 `has_java_method()`：`JNISingleton` 的 Java 方法不进 `ClassDB`，`has_method()` 恒为 false（见 `platform/android/api/jni_singleton.cpp`）；若引擎版本没有该 API 则乐观放行 |
| 后台起服务被拒 | `startServiceCompat()`（`android/plugins/GDMusicBackgroundAudio/GDMusicBackgroundAudioPlugin.java:151`）捕获 `IllegalStateException` / `SecurityException`，只打 logcat，Godot 侧继续播 |
| 通知权限被拒 | 通知不显示但服务正常；`requestNotificationPermission()` 只请求一次（`_notification_permission_requested` 守卫，`:1128`） |
| 同一状态重复推送 | 600ms 节流 + 键值比对，键不变直接 return |
| 耳机键连击下一首 | 服务侧 `SKIP_THROTTLE_MS = 400L` 去抖（`:276`） |
| 封面下载失败 | 服务保留无图通知，不阻塞状态推送 |
| 服务在 `onDestroy` 前崩溃 | `START_STICKY`，系统会重建服务；重建后靠下一次 `updatePlayback` 恢复元数据 |
| 后台巡检发现播完、但队列为空 | `on_audio_finished()` 的 `has_tracks()` 守卫直接返回，不会误切或清空播放态 |
| tick 与延迟到达的 `finished` 撞车 | 1500ms 去重窗 + 陈旧信号守卫，同一次播完只处理一次（§4.10） |
| 后台加载下一首失败 | 连续失败熔断（`_is_background_error_streak_exceeded()`）停播并给出 `last_error`，不会几十毫秒刷完整个队列 |

## 8. 已知限制与后续

- **任务描述与实际文件不符**：后台媒体控制代码在 `music_app_audio_controller.gd`，不存在 `music_app_playback_state_controller.gd`；`assets/scripts/ui/music_app/music_app_showcase.gd:57` 里变量名仍叫 `_playback_state_controller`，是历史命名。本文以真实代码为准。
- **只支持 arm64-v8a**：`export_presets.cfg` 未开 x86_64，模拟器上插件与 libmpv 都不会工作。
- **进度条依赖 1 秒推送**：`PLAYBACK_STATE_REFRESH_MS` 是功耗与观感的折中；进一步可改成只在 seek/暂停时推、其余交给 `speed` 外推，但小米系 ROM 会漂移，暂不采用（推断）。
- **通知栏自绘布局未做**：`RemoteViews` 自定义外观可以更接近主流播放器，但需要额外资源与兼容性测试。
- **无自动化测试**：服务逻辑只能靠真机回归；未来可考虑 `androidTest` 覆盖 `onStartCommand` 的分支与节流。
- **两项验收未闭环**：音量只有「控件与下发链路已验证」的结论，真机听感未确认；拔耳机自动暂停因为 `adb` 拿不到 `INJECT_EVENTS` 权限，一直是手工项。
- **iOS 完全空白**：本篇只覆盖 Android。iOS 的同等功能要靠 `AVAudioSessionCategoryPlayback` + `UIBackgroundModes: audio`，没有前台服务也没有 MediaSession，控制中心走 `MPNowPlayingInfoCenter`（详见 [libmpv原生扩展](2026-10-27_libmpv原生扩展.md) §8）。
- **节流键不含位置是有意为之**：常规推送 600ms 节流键是 `title|artist|playing|duration`，拖动进度时必须绕开（§4.4）；后续若给节流加位置字段，反而会把「拖动中的高频位置」全部放行，把服务打满——不要「顺手修」。
