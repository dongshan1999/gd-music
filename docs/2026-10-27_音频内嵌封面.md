# 音频内嵌封面（功能实现文档）

| 项目 | 内容 |
| --- | --- |
| 文档日期 | 2026-10-27 |
| 对应代码版本 | develop @ 91d939d（工作区 2026-10-27） |
| 功能分类 | 播放内核 / 应用界面 |
| 覆盖范围 | `assets/scripts/save/music/audio_artwork_reader.gd`（ID3 / FLAC / MP4 / Ogg / RIFF 解析）、状态控制器里的封面缓存与下发、播放页与迷你播放器的占位回退、通知栏封面 |

> 一句话定位：App 不额外保存封面，而是每次需要时从音频文件自己的标签里「就地抠一张图」——只读文件头和元数据块，不碰音频数据；抠出来落盘缓存，抠不到就退回主题色占位图。

## 1. 功能概述

- 用户视角：本地导入的 mp3/flac/m4a/wav 在播放页、迷你播放器、进度通知栏都能看到专辑图；没有内嵌封面的曲目显示统一的占位图标，不会留一块空白或显示上一首的旧图。
- 实现视角：
  - 解析器 `AudioArtworkReader`（`assets/scripts/save/music/audio_artwork_reader.gd`，517 行，`class_name AudioArtworkReader`）是一个**纯静态工具类**：不解码音频、不依赖任何编解码扩展（文件头注释 `:4-8`），返回 `{"mime": String, "data": PackedByteArray}`。
  - 调用与缓存集中在 `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd`（`get_track_artwork_source()` `:1260` 起）。
  - 展示在 `views/player/music_app_player_view.gd`、`views/mini_player/music_app_mini_player_view.gd`、以及通知栏（Java 侧 `updateArtwork`）。
- 不在本期范围：从网络曲库按专辑搜封面、用户自定义封面、写回/替换音频里的封面标签。

## 2. 功能入口与调用链

封面没有独立入口，它是「曲目切换」的副产物：

1. 曲目切换 → 状态控制器 `request_audio_sync()`（见[播放状态与全局控制](2026-10-27_播放状态与全局控制.md)）。
2. 播放页/迷你播放器监听播放事件后各自刷新：
   - 播放页 `_refresh_artwork(track)` `assets/scripts/ui/music_app/views/player/music_app_player_view.gd:540`，用 `曲目 id|source` 做键，键不变直接 return（`:564-570`）。
   - 迷你播放器 `_refresh_cover(track)` `assets/scripts/ui/music_app/views/mini_player/music_app_mini_player_view.gd:119`，同样先查 `_artwork_texture_cache`（`:139`）。
3. 两者都问 `get_track_artwork_source(track)` `assets/scripts/ui/music_app/controllers/global/music_app_audio_controller.gd:1260`：**插件封面地址优先，本地内嵌封面兜底**（`:1261-1264`）。
4. 本地分支 `_get_local_embedded_artwork_source()` `:1278` → `_ensure_local_artwork()` `:911` → `AudioArtworkReader.read_embedded_artwork()` `assets/scripts/save/music/audio_artwork_reader.gd:19`。
5. 返回的是 `user://gdmusic-artwork/<md5>.<ext>` 的图片文件路径，视图再按来源类型加载（http 下载 / SAF 读字节 / `Image.load_from_file`）。
6. 通知栏单独一路：`_push_notification_artwork()` `:1238` 把图压成 base64 JPEG 交给 Java 侧，同一首只推一次（键是 `track.id` + source，`:1243-1247`）。

## 4. 关键实现

### 4.1 容器嗅探：只读 12 字节决定解析器

```gdscript
var header := file.get_buffer(12)
if header.size() >= 10 and _ascii(header, 0, 3) == "ID3":
	result = _read_id3(file)
elif header.size() >= 4 and _ascii(header, 0, 4) == "fLaC":
...
elif header.size() >= 12 and _ascii(header, 4, 4) == "ftyp":   # mp4/m4a
```

`read_embedded_artwork()` `:19-46` 先开文件读 12 字节，按魔数分派到 5 个解析器：`ID3`（mp3/部分 wav）、`fLaC`、`ftyp`（注意 m4a 的前 4 字节是 `atom size`，所以 `ftyp` 在偏移 4）、`OggS`、`RIFF`（wav）。分派完一次性 `_finalize()` `:50-61` 收口：空数据、超过 8MB、mime 为空或只有 `image/` 前缀时用 `_sniff_mime()` `:65` 按文件头再猜一次（JPEG `FF D8 FF`、PNG `89 50 4E 47`、WEBP `RIFF....WEBP`、GIF），仍然认不出就丢。

**为什么只读 12 字节**：一次播放切歌可能触发 5 处刷新（播放页大图、迷你播放器、通知栏、锁屏、播放队列列表），每次整文件读入会让 5MB 的 flac 变成 25MB 的 IO 与内存抖动。分派之后所有解析器都用 `FileAccess.seek()` 跳着读。

### 4.2 ID3v2：APIC 帧

`_read_id3()` `:131-175` 的处理顺序与该踩的坑：

1. header 10 字节：`major = header[3]`、`flags = header[5]`、`tag_size = _syncsafe(header, 6)`（`:132-137`）——**ID3 的长度是 7-bit syncsafe 整数**，不是普通大端，按大端解会读到垃圾长度。
2. 整段标签读入后按 `flags & 0x80` 决定是否 `_deunsync()` `:111`（v2.3 的 unsynchronisation 把 `0xFF` 写成 `0xFF 0x00`，不还原会破坏 JPEG 里的 `FF D8`）。
3. `flags & 0x40` 的扩展头必须跳过：v2.4 是 syncsafe 长度，v2.3 是「4 字节自身长度 + 数据」，代码用 `major >= 4` 区分（`:150-153`）。
4. 帧头长度：v2.2 是 6 字节、帧 id 3 字节；v2.3/v2.4 是 10 字节、帧 id 4 字节（`:155-164`）。
5. 帧大小：v2.4 用 syncsafe，v2.3 用大端（`_frame_size()` `:104-107`）。
6. 命中 `APIC`（v2.2 是 `PIC`）立即返回，不再往后扫（`:171-172`）。

`_parse_id3_apic()` `:179-221` 的字段顺序是「编码 1 字节 → mime（v2.2 是 3 字节 `PNG`/`JPG`，v2.3+ 是 0 结尾字符串）→ 图片类型 1 字节 → 描述（编码为 UTF-16 时按 2 字节对齐找连续两个 0）→ 剩余即图片字节」。**描述文本的结束判断是最容易写错的地方**：UTF-16 的终止符是 `00 00`，但如果按单字节找 0，会在 ASCII 名字的第一个字符后就截断，导致封面被切掉半张。

### 4.3 MP4/M4A：递归 atom 树里的 `covr`

`_walk_mp4()` `:294-334`：

- 每个 atom 头 8 字节（大端 size + 4 字符 type）；`size == 1` 表示后面跟 8 字节 64 位长度（大文件必需），`size == 0` 表示「一直到父级末尾」（`:306-313`）。
- 只递归 `moov` / `udta` / `ilst` / `trak` / `mdia` 五类容器（`:329`），**`meta` 特殊**：它和它下面的 atom 之间多 4 字节 version+flags，因此递归起点是 `body_start + 4`（`:324-326`）。这一步写错就会得到「m4a 有封面但永远读不到」。
- 深度上限 8（`:295`），防止畸形文件构造超深嵌套把栈打穿。
- `covr` 里是一个或多个 `data` 子 atom，data 头 8 字节（4 字节 type + 4 字节 locale），`data_type & 0x00FFFFFF` 为 13 表示 JPEG、14 表示 PNG（`:353-363`），payload 长度是 `atom_size - 16`。

### 4.4 FLAC 与 Ogg

- FLAC：跳过 4 字节 `fLaC` 后逐个 metadata block 走，`block_type == 6` 即 `PICTURE`（`:237-244`），最多走 64 个 block（`guard < 64` `:232`）——正常文件只有几个 block，上限只是防坏文件死循环。
- Ogg/Opus：在前 256KB 里找 `\x03vorbis` 或 `OpusTags` 标记（`:379-385`），跳过 vendor 字符串，遍历 comment，最多 256 条（`:402`），只认大写后的 `METADATA_BLOCK_PICTURE`，其值是 **base64 编码的 FLAC PICTURE 结构**（`:419-428`）。
- 两个格式共用 `_parse_flac_picture()` `:252-282`：图片类型 4 字节 → mime 长度 4 + mime → 描述长度 4 + 描述 → 宽高色深索引色共 16 字节 → 数据长度 4 + 数据。所有长度都做 `position + n > buffer.size()` 的越界检查，宁可返回空也不能崩。

### 4.5 WAV：RIFF 里的 `id3 ` 块

`_read_wav()` `:452-481` 从偏移 12 开始遍历 chunk，找 `id3 ` / `id32` 块，把整块当独立 ID3 解析（`_read_id3_from_buffer()` `:485` 复用同一套帧遍历）。两个细节：chunk 大小按**偶数字节对齐**（`:479`），并且 `guard < 128` 限制遍历次数。

### 4.6 性能：为什么能只读必要字节

| 设计 | 效果 |
| --- | --- |
| 12 字节嗅探后 `seek` 分派 | 不会整文件读入 |
| ID3/FLAC/WAV 用 `FileAccess.get_buffer()` 精确读块 | 只读标签区，音频数据一个字节都不碰 |
| 命中 APIC/PICTURE/covr 立即返回 | 不扫完整个标签（大部分文件还有 TIT2/TPE1 等帧） |
| Ogg 只扫前 256KB | 注释头一定在文件开头，避免大文件全扫 |
| 帧大小越界/为 0 立即 `break` | 坏文件在几十次读之内结束，不会卡死 |

### 4.7 两级缓存与内存管理

`_ensure_local_artwork()` `:911-945` 是「路径级」缓存，负责把标签里的图片**落盘**并记住结果：

```gdscript
var cache_key := source_path.md5_text()
if _local_artwork_sources.has(cache_key):
	var known := str(_local_artwork_sources[cache_key])
	if known.is_empty() or FileAccess.file_exists(known):
		return known
	_local_artwork_sources.erase(cache_key)
```

- 键是**源路径的 md5**（不是完整路径），既省内存又避免路径里的特殊字符进文件名；文件名 `user://gdmusic-artwork/<md5>.<jpg|png|webp|gif>`（`:937`）。
- 负缓存：`data` 为空时存 `""`（`:926`），下次不再读文件。**没有负缓存的话，一首无封面的歌每刷新一次都要重新开文件扫标签**。
- 缓存项会校验文件是否还在（`FileAccess.file_exists(known)`），用户清缓存后自动重算。
- 写盘失败也记 `""`（`:939-941`），避免每次都尝试写一个写不进去的路径。

`_resolve_artwork_payload()` `:1303-1316` 是「编码级」缓存：同一来源的 base64 JPEG 只算一次，`_artwork_inflight` 防止同一张图的并发下载。它内部 `_encode_artwork()` `:1354-1375` 会把长边限到 `ARTWORK_MAX_EDGE`（512）并统一重编码成 JPEG（质量 `ARTWORK_JPEG_QUALITY` = 0.85）——**只有通知栏这条链路需要编码**，视图直接用原图纹理。

### 4.8 读不到封面时怎么回退

| 层 | 行为 |
| --- | --- |
| 解析器 | 返回 `{}`，不抛错、不打印（安静失败） |
| 控制器 | `_local_artwork_sources[key] = ""` 并返回 `""` |
| 播放页 | `_refresh_artwork()` 里 source 为空 → 隐藏 `album_artwork_rect`、显示 `cover_icon_rect` 占位 |
| 迷你播放器 | `_apply_cover_placeholder()` `assets/scripts/ui/music_app/views/mini_player/music_app_mini_player_view.gd:154` 恢复图标与默认底色（`DEFAULT_COVER_BG`/`DEFAULT_COVER_FG`） |
| 通知栏 | source 为空时显式推 `""` 给 Java 侧 `updateArtwork("")`（`:1248-1251`）——**不清的话通知栏会一直挂着上一首的封面** |

插件曲目还有个跨来源的兜底：`get_track_artwork_source()` 先看插件给的 `artwork`，没有才去读本地内嵌（`:1261-1264`）；反过来「插件给了封面但它 404」不会回退到本地（那需要先判断下载状态，当前实现没做）。

### 4.9 与「曲目编辑」的关系：只改文字，不写封面

`MusicAppTrackEditController`（`assets/scripts/ui/music_app/controllers/music_app_track_edit_controller.gd`，48 行）的注释写得很明确（`:4`）：「编辑当前播放曲目的歌名 / 创作者，只改本机曲库与下载记录，不回写音源平台」。`save_track_info()` `:19-36` 只动 `track.title` / `track.artist`，然后 `normalize()` + `save(false)`；已下载曲目顺便同步下载记录的标题（`_sync_download_record()` `:39-48`）。

所以：

- **封面从不被写入**：编辑标题不会影响封面来源，也不会把封面「固化」进曲库。
- 编辑后封面不会变：封面键是 `track.id`（不变），解析缓存键是文件路径（不变），因此不会触发重新解析——这是期望行为。
- 想换封面只能换音频文件本身（或换插件来源），代码里没有「设置封面」入口。
- 用下载记录里的 `path` 而不是 `track.file_path` 来找封面（`_get_local_embedded_artwork_source()` 只认 `file_path`）——**下载的插件曲目**如果能拿到插件 `artwork` 就用在线图，拿不到就走占位图；本地文件的内嵌封面只对本地扫描曲目生效（推断自 `:1281-1285` 的实现，下载记录路径未参与）。

## 5. 边界与失败处理

| 场景 | 行为 |
| --- | --- |
| 文件不存在 / 打不开 | `read_embedded_artwork()` 返回 `{}`（`:20-25`） |
| 封面超过 8MB | 丢弃（`_finalize()` `:54`），避免异常标签占内存 |
| mime 缺失或是 `image/` 空前缀 | 按文件头嗅探；仍认不出则丢弃 |
| ID3 标签超过 24MB | 只读前 24MB 解析，可能读不到 APIC 但不会 OOM |
| 标签里没有 APIC/PICTURE/covr | 返回 `{}` → 负缓存 → 占位图 |
| tag/frame 长度为 0 或越界 | 立即 `break` 返回空，不崩 |
| ogg 注释头在前 256KB 之外（畸形文件） | 读不到，返回空 |
| mp4 atom 嵌套过深 / 长度非法 | `depth > 8` 或越界即停 |
| SAF 虚拟路径（`saf-tree://`、`content://`） | 解析器只接受真实路径；调用方先 `_materialize_local_source()` `:871` 物化到缓存目录再解析 |
| 播放时物化文件已被系统清掉 | `:1298` 检查 `FileAccess.file_exists(materialized)`，不存在则返回 `""` |
| 远端封面请求超时/非 2xx | `_download_artwork_bytes()` `:1332-1351` 返回空字节 → 本次无封面，不缓存失败结果 |
| 同一张图并发请求 | `_artwork_inflight` 去重，后到的直接返回空串 |

## 8. 已知限制与后续

- 只能读**内嵌**封面：不给「同目录同名 `.jpg`/`folder.jpg`」兜底，也没有网络反查。
- 无法写回/替换封面：编辑弹窗只改文字；要实现「换封面」得重写容器标签（mp3 可追加 ID3v2，m4a/mp4 需要重排 atom），风险高，本期未做。
- 插件封面 404 时不会回退到本地内嵌图（`get_track_artwork_source()` 只看来源字符串，不做可用性预判）。
- 下载的插件曲目不会被当作「本地内嵌封面」来源（只查 `track.file_path`），因此完全离线时这类曲目只能显示占位图——若要支持，应在 `_get_local_embedded_artwork_source()` 里补一条下载记录路径的分支。
- `_artwork_bytes_cache` / 视图的 `_artwork_texture_cache` 都是进程内无上限字典，长时间连续切歌（几百首、每首不同封面）会累积内存，目前只靠重启释放。
- `MAX_ID3_TAG_BYTES`（24MB）在极端大标签上仍会一次性读入，移动端低内存设备可能吃紧（推断）。
